# Synthetic Data Generator

Projects and teaching demos routinely describe an input shape ("upload a
bank statement CSV", "paste a meeting transcript", "a batch of support
tickets") that the build steps then assume exists. Left unhandled, this
either blocks the demo on the user finding a real file, or gets invented
ad hoc and inconsistently by whichever builder skill hits it first. This
skill is the one place that turns a brief's described input shape into
real, checked-in sample files.

## When to use

- After `technical-design` (projects/concepts) or `teaching-brief`
  (teaching demos) produces an approved design/brief that names a
  concrete input data shape — before the component-build skills that
  consume that data run (`backend-fastapi`, `vector-store`, the
  `agent-*` skill, `frontend-*`, or `teaching-build`).
- Any time `write-and-validate-tests`'s happy-path test case needs a
  concrete file to exercise, and none exists yet.
- Skip entirely if the brief already supplies real sample data, or if the
  input is pure free-text typed at runtime with no file/dataset behind it
  (e.g. a simple single-turn Q&A with no upload).

## Procedure

1. **Read the brief/design, not just the app description.** Extract:
   - What file type(s) the app consumes (CSV, PDF, plain text transcript,
     JSON, log lines, images, etc.).
   - The schema/structure implied (column names, transcript speaker
     format, ticket fields) — infer from the brief's own examples and
     `write-and-validate-tests`'s draft happy-path case if it exists yet;
     ask the user only if the shape is genuinely ambiguous after checking
     both.
   - Roughly how much data is needed to make the demo feel real without
     being a testing burden (a handful of realistic rows/transcripts is
     almost always right for a 2-hour build — tens, not thousands, unless
     the brief specifically calls for scale/volume testing).
2. **Generate with code, not a live LLM call.** Write a small local
   script (Python `random`/`faker`-style generation, or hand-authored
   realistic text) that produces the files deterministically (fixed seed)
   so re-runs are reproducible and no API cost is incurred. Do not route
   this through `_shared/llm_client.py` — this is local synthesis, not a
   product feature, and burning a real provider call here would violate
   this repo's API-cost-approval rule for something that doesn't need it.
   Exception: if the brief specifically wants LLM-generated realistic
   prose (e.g. varied natural-sounding support tickets) and the user has
   already approved API spend for this purpose with a cost estimate, that
   generation may use the real provider — but default to hand-authored/
   templated synthesis first and only escalate to a real call if templated
   output would be too repetitive to demo well.
3. **Write output to the right location:**
   - `projects/<slug>/data/` for a project.
   - `concepts/<slug>/data/` for a concept.
   - `teaching/<slug>/data/` for a teaching demo.
4. **Always write `data/README.md`** documenting, per file:
   - What it is and why it exists (which brief requirement it satisfies).
   - Its schema/structure.
   - Which notebook, app, or test case consumes it.
   - That it is synthetic, not real user data — explicit, so nobody later
     mistakes it for a real dataset.
5. **Keep it realistic enough to demo, not exhaustive.** Include at least
   one edge case relevant to the app's logic (e.g. a duplicate customer
   across two tickets so memory recall has something to find, a
   subscription charge that repeats monthly so a finance advisor has
   something to flag, a transcript with an ambiguous action-item owner).
   A flat, edge-case-free dataset makes for a boring demo and under-tests
   the app's actual logic.
6. **Never overwrite real user-supplied data.** If `data/` already
   contains files not generated by this skill (no matching README entry
   marking them synthetic), stop and ask before touching that folder.
7. Report back: which files were created, their location, and one
   sentence on what edge case(s) were seeded in, so the calling
   pipeline/user knows what to expect when demoing against them.
