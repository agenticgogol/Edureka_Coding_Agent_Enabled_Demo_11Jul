Concept 00 · Foundations

Agent Architecture

The mechanics underneath Claude Code's subagents, hooks, and sessions — the same loop, coordinator model, and enforcement rules the Claude API and Agent SDK are built on. Read this before Parts 4 and 6 for the "why," not just the "how."

1.1

The agentic loop, and why stop_reason is the only honest termination signal

Every agent — Claude Code included — runs the same mechanical loop underneath: send the full message history plus the available tools, get back an assistant response, check one field, and branch. That field is stop_reason. It's not a suggestion or a summary — it's the API telling you, structurally, why generation stopped.

Four values do the real work: tool_use (run the pending tool calls and go around again), end_turn (the turn is genuinely done), max_tokens (truncated — treat as failure, not completion), and stop_sequence (a configured string fired — also not completion). Everything people get wrong about "detecting when the agent is done" comes from replacing this field with something softer: parsing the model's prose for "anything else?", checking an iteration counter, or assuming a text block means the turn finished. All three fail, because the model can write "let me check that" in the same response as a pending tool call, and can also finish silently with no closing remark at all.

The loop has exactly one branch point. max_tokens and stop_sequence are not shown as a third arrow because they aren't a path forward — they're a signal to stop and handle as failure.
1.2

Coordinator and subagent systems: hub-and-spoke, and the context boundary

A single agent has one context window and does one thing at a time. That's fine until a task has several independent parts, each producing a lot of intermediate material — Claude Code's own subagents (Part 4) exist for exactly this reason. The architecture that results is hub-and-spoke: a coordinator decomposes the goal, delegates a task prompt down to each subagent, and aggregates the summary that comes back up. There is deliberately no lateral channel — subagents cannot see or message each other.

This isn't a limitation to work around; it's the entire reason isolation works. Coverage of the final answer is capped by how the coordinator decomposed the problem — a subtask nobody was assigned to (distribution, regulation, an unnamed competitor) doesn't get noticed by any subagent, because none of them ever saw the whole question. More subagents or a bigger context window fix nothing here; only better decomposition does.

Context moves down as a prompt and back up as a summary — it never moves sideways between subagents
1.3

Spawning subagents: the Task tool, allowedTools, AgentDefinition, and parallel spawning

Delegation happens through a specific tool — historically named Task in Claude Code (current Agent SDK docs call the same mechanism the Agent tool; both names refer to the same thing). The coordinator's allowedTools must include it, or nothing errors — the subagent definitions still exist, the system prompt still says "delegate" — the coordinator just quietly does all the work itself, in its own context, because it has no way to actually hand it off.

Each subagent is defined by an AgentDefinition: a description the coordinator reads to decide routing, a prompt that sets the role and the output shape the coordinator will parse, and a tools list that's a hard boundary, not a hint — no Write tool means no write mistakes are possible, full stop. Independent subtasks should run at the same time: the mechanism is that the coordinator emits several tool-use blocks for the same tool in a single response. The runtime sees multiple pending calls in that one response and executes them concurrently — parallelism is a property of the message shape, not a configuration flag.

Where the Task calls sit in the response — not a setting — decides whether work runs in parallel or in sequence
1.4

Programmatic enforcement against prompt guidance

A rule written into a system prompt or CLAUDE.md — "never issue a refund before identity is verified" — holds most of the time. Most of the time is a description of a probability, not a control. The alternative is a prerequisite gate: a check in the tool-executing layer, outside the model's discretion entirely, that refuses to run a tool until a condition is satisfied. In Claude Code terms, this is a PreToolUse hook (Part 6) doing what a line in CLAUDE.md only describes.

The gate should fail usefully, not just fail: return a structured refusal the model can act on ("blocked: no verified customer id — call get_customer first"), not a bare error string that strands the model with no path forward. Done right, the model repairs the situation itself — calls the missing prerequisite, then retries — and the rule holds even if the system prompt is ignored entirely, because enforcement never depended on the model reading it.

Same rule, two different places it can live — only one of them is a control rather than a hope
1.5

Hooks: PostToolUse normalization, and interception before a call runs

A hook is code your process runs at a fixed point in the loop, outside the model's discretion — the model cannot decide to skip it, argue with it, or forget it. Around any single tool call, your code effectively sits in two places: interception before the call (a PreToolUse hook that can allow or block, returning a structured reason on block rather than letting the call silently vanish), and normalization after it (a PostToolUse hook that can rewrite the raw result before it's appended to history).

The normalization point matters more than it looks: whatever the PostToolUse hook writes back is the tool result as far as the model is concerned. That's the mechanism behind auto-formatting a file after every edit (Part 6) — the hook isn't suggesting a cleanup, it's redefining what "the result of this edit" means before the model ever sees it.

Nothing the model asked for reaches the tool without passing the first hook; nothing the tool produced reaches history without passing the second
1.6

Prompt chaining against dynamic decomposition

There are two ways to break a large task into smaller ones. Prompt chaining fixes the steps at design time — extract, then validate, then format — each step separately testable, predictable, and cheap to reason about. Dynamic decomposition hands the model a goal, constraints, and tools, and lets it choose the next step at run time — two similar-looking inputs can take entirely different paths and cost different amounts.

The test for which one to use: if you can write the steps down before you see the input, chain it. If the right sequence genuinely depends on what the input turns out to be, decompose dynamically and accept the variance. A common hybrid worth naming explicitly is the per-file pass plus integration pass — Claude Code doing something like "update every file independently, then run one final pass to reconcile the changes into a coherent whole" — a fixed chain (per-file, then integrate) wrapping a dynamic step (what actually changes per file).

Chaining buys predictability; dynamic decomposition buys reach — choose by whether the steps are knowable in advance
1.7

Sessions: --resume, --fork-session, and when a fresh session beats a resumed one

Three moves are available from any point in a session. --resume (or /resume) continues writing to the same session — good when the stored context is still true and you just want to keep going. --fork-session (or /branch) copies the full conversation up to that point into an independent new session and switches you into it — same past, independent futures — leaving the original completely untouched, so you can compare two approaches and keep whichever one worked.

The third move is starting fresh with a written summary instead of resuming or forking: decisions, constraints, and the next step — no raw tool-result listings, no abandoned approaches carried along as dead weight. Choose based on one question: are the old tool results and context still true? If yes, resume. If you want to try something different without risking what you have, fork. If the session has accumulated enough dead ends that even a fork would drag them along, summarize and start clean instead.

The choice is about whether the old tool results are still true, not about how much context you'd like to keep

Key Takeaways

  • stop_reason is the only structural signal in the loop — every other way of detecting "is it done" (parsing prose, counting iterations, checking for a text block) is a workaround that fails on real transcripts
  • The hub-and-spoke shape is what makes subagent isolation safe — no lateral channel means no subagent can be confused by another's half-finished reasoning, but it also means decomposition quality sets a hard ceiling on the final answer
  • allowedTools is a silent failure point — miss the Agent/Task tool and the coordinator does everything itself with zero error message, not a crash you'd notice
  • Guidance and enforcement are architecturally different things — a rule in a prompt is a probability; a prerequisite gate is a control, and only one of them survives an adversarial or confused conversation
  • A PostToolUse hook doesn't clean up the result — it redefines it — whatever the hook writes back is the only result the model ever sees
  • "Can I write the steps before seeing the input" is the actual decomposition test — not team size, not task complexity
  • Forking exists so experimentation never costs you the working baseline — the real failure mode it prevents is resuming into an existing session and blurring two attempts together

Hands-On

  1. Watch stop_reason directly, not through the UI

    commandclaude -p "List the files in this repo, then summarize what this project does" --output-format json

    Find stop_reason in the raw JSON on the intermediate step where it calls a tool, versus the final response. Confirm the first is tool_use and the last is end_turn.

  2. Prove the "no lateral channel" rule to yourself

    promptUse two subagents: have one explore how authentication works and another explore how billing works. Then ask the billing subagent what the auth subagent found.
    Expected: it can't answer — only the coordinator (you, in the main session) has both summaries. Nothing crosses between subagents directly.

  3. Break allowedTools on purpose

    Create a subagent, then explicitly remove the Agent/Task tool from your session's allowed tools and ask for the same delegation. Confirm it silently does the work itself instead of erroring — this is the failure mode the theory warns about.

  4. Build the same rule two ways

    promptAdd "never run a destructive migration script without confirming a backup exists" to CLAUDE.md. Then separately, add a PreToolUse hook that actually checks for a recent backup file before allowing that script to run.

    Try to talk your way past each version in conversation. Confirm only the hook-enforced version can't be argued around.

  5. Build an interception hook and a normalization hook, back to back

    promptAdd a PreToolUse hook that blocks any Bash command touching a .env file, and a PostToolUse hook that wraps every Edit tool result in a consistent JSON shape with a status field.

  6. Deliberately pick the wrong decomposition, then fix it

    Ask Claude Code to "add input validation to these 5 files, then write one summary of what changed" — notice it does a per-file pass followed by one integration pass, and compare that to asking it to do all 5 files "as one giant dynamic task" instead.

  7. Practice all three session moves in one sitting

    commandsclaude --continue
claude --resume <session-id> --fork-session
/branch try-alternate-approach

    Deliberately fork before a risky refactor, try it in the fork, and confirm the original session is untouched if it goes badly.

Certification Prep — Can You Answer These?

  • Why is checking stop_reason more reliable than parsing the model's text for phrases like "let me know if you need anything else"?
    A: stop_reason is a structural field the API always returns; the model's prose can say something that sounds like completion in the same response as a pending tool call, or finish silently with no closing remark at all. Programmatic branching must read the field, not the sentence.
  • Which two stop_reason values get mistaken for completion when they actually indicate the response is incomplete?
    A: max_tokens (output was truncated mid-thought) and stop_sequence (a configured string fired). Neither means the work finished — both should be treated as failure states, not success.
  • Why can't two subagents in a coordinator/subagent system communicate directly?
    A: There's no lateral channel by design — context only flows down as a task prompt from the coordinator and back up as a summary; this keeps each subagent's context clean but means the coordinator is the only thing that ever sees the whole picture.
  • A subagent's context window is described as "not empty" even though it starts fresh. What does it actually contain?
    A: Its own AgentDefinition (system prompt) and the single task prompt the coordinator gave it — nothing from the coordinator's conversation, the overall plan, or any sibling subagent's findings.
  • What happens if a coordinator's allowedTools is missing the Agent/Task tool, and why is that dangerous?
    A: Nothing errors. The AgentDefinitions still exist and the system prompt still says to delegate, but the coordinator silently does all the work itself in its own context — a failure mode with no error message to notice.
  • Why does a rule written only in a system prompt fail differently than the same rule enforced by a prerequisite gate?
    A: The system prompt version holds at a rate you can measure, never at a rate you can promise — it's a probability. A prerequisite gate is a check in the tool-executing layer that blocks the call outright regardless of what the model decided, so it holds even if the system prompt is ignored entirely.
  • What's the functional difference between a PreToolUse hook and a PostToolUse hook?
    A: PreToolUse can block a call before it ever runs (interception); PostToolUse only runs after the tool executes, so it can rewrite or normalize the result but can't prevent the underlying action.
  • What's the actual test for choosing prompt chaining over dynamic decomposition?
    A: Whether you can write the steps down before you see the input. If yes, chain it — predictable and separately testable. If the right sequence genuinely depends on the input, decompose dynamically and accept the variance in path and cost.
  • When would you choose --fork-session over --resume?
    A: --resume continues writing to the same session — fine when the stored context is still valid. --fork-session copies the conversation into an independent new session first, so you can try a different approach without risking the working original — pick it whenever the next step is an experiment, not a continuation.

Part 01 · Orientation

Fundamentals

What Claude Code actually is, the surfaces it runs on, how permission works, and the everyday loop you'll spend 90% of your time in.

Theory

Claude Code is an agent that operates inside your codebase rather than beside it in a chat window. You describe a task in plain English; it reads the relevant files, forms a plan, edits code, runs commands (tests, builds, git), and verifies its own work — the same loop a developer runs, just executed by the model with you supervising.

That loop runs identically across every surface it's exposed through: the terminal CLI, Claude Code on the web, the VS Code/JetBrains extensions, the Desktop app, Slack via Claude Tag, and headless inside GitHub Actions/GitLab CI. Nothing about the agent changes — only where it runs and how you trigger it. Your CLAUDE.md, skills, subagents, and hooks apply identically no matter which surface you're in.

The other load-bearing concept here is the permission model: by default, Claude Code stops and asks before it edits a file or runs a shell command, showing you the diff or the exact command first. This is the safety net that makes an autonomous agent workable — you can pre-approve safe, narrow patterns (like Bash(git diff:*)) so you're not clicking through routine actions, while leaving anything destructive gated behind a real approval.

Same agent, six entry points — CLAUDE.md, skills, hooks and permissions apply identically to all of them

Key Takeaways

  • Claude Code is one agent wearing six outfits — the terminal, web, IDE extensions, Desktop, Slack, and CI are all the same underlying loop; master one and you've effectively learned all of them
  • The permission prompt is the whole safety model — it's not friction to escape, it's the single mechanism standing between "agent that edits code" and "agent that edits code unsupervised"
  • Pre-approving is a scoping exercise, not a convenience toggle — the skill is writing narrow patterns like Bash(git diff:*), never a blanket Bash(*)
  • CLAUDE.md is the only file guaranteed to be read — everything else you'll build (skills, hooks, subagents) is optional and conditional; this one always loads
  • /clear and /compact solve different problems — clear when the task changed, compact when the task is the same but the conversation got long

  3. Generate CLAUDE.md

  4. Make one real change

  5. Practice the git loop

    promptStage the changes, write a clear commit message, and open a PR.

  6. Learn the session-state commands

    Try each of these in order and notice what changes:

Certification Prep — Can You Answer These?

  • What's the actual difference between Claude Code running in the terminal versus running headless in a CI pipeline?
    A: Nothing about the agent itself — same loop, same tools, same reasoning. The only difference is the UI: headless mode strips it out and runs non-interactively via -p, which is exactly what a CI job does.
  • Why is a blanket Bash(*) allow rule considered a serious mistake, not just risky?
    A: It hands the agent unrestricted shell access, which defeats the entire purpose of the permission system — the model can now run destructive commands (rm -rf, force-push, deploy scripts) without any approval gate at all.
  • If CLAUDE.md and a skill both exist, which one is guaranteed to be read at session start?
    A: CLAUDE.md. Skills only load their full body when a request matches; only CLAUDE.md is unconditionally read into context on every session.
  • When should you use /clear instead of /compact?
    A: /clear when you're switching to an unrelated task and want zero carryover context; /compact when you're still on the same task but the conversation has gotten long and needs summarizing rather than wiping.

Part 02 · Extensibility

Skills

The core extensibility layer — packaged, on-demand expertise that Claude discovers and loads automatically.

Theory

A skill is a folder containing SKILL.md — YAML frontmatter (name, description) plus markdown instructions. At session start, Claude Code loads every skill's description into context — cheap, since it's just one line each. The full body only loads when a request actually matches, or when you invoke it directly with /skill-name.

This two-tier loading is the entire reason skills are powerful: you can bundle enormous amounts of reference material, scripts, and templates into a skill's references/, scripts/, and templates/ subfolders, and none of it costs context until Claude actually opens it for a matching task.

Skills live at three scopes — personal (~/.claude/skills/), project (.claude/skills/, committed to git), or packaged inside a plugin for org-wide rollout — and can also be nested inside a monorepo subdirectory so they only fire when you're working in that specific area.

Descriptions are always loaded; bodies and reference files load only on a real match

Key Takeaways

  • The description field does the routing, not the body — a perfect SKILL.md with a vague description never fires; a mediocre one with sharp trigger phrases works every time
  • Two-tier loading is what makes skills scale — cheap description always in context, expensive body only on a real match — this is the mechanism, not an implementation detail
  • scripts/ beats regenerated code — deterministic, token-efficient, and reliable in a way that asking Claude to "write the same validation logic again" never quite is
  • A skill that fires too often is as broken as one that never fires — over-triggering pollutes unrelated conversations just as badly as under-triggering leaves you re-explaining yourself
  • Scope decides who benefits — personal skills help only you; project skills (committed) help your whole team the moment they clone the repo

Hands-On

  1. Pick a real repeated task

    Something you've explained to Claude 3+ times already.

  2. Scaffold the folder

    commandmkdir -p .claude/skills/my-skill

  3. Ask Claude to draft it

    promptI keep re-explaining the same task: [describe it]. Draft a SKILL.md for a skill called "my-skill" in .claude/skills/my-skill/. Write the description in third person and list the literal phrases I'd type to trigger it.

  4. Tighten the description by hand

    This is the one field you should never fully delegate — only you know your team's real phrasing. Rewrite it to name the exact trigger phrases your team uses, in third person: "This skill should be used when the user mentions X, Y, or asks to Z" — not a generic summary of what the skill does.

  5. Move bulk material into references/

    promptTake this document [paste or point to file] and reorganize it into .claude/skills/my-skill/references/, chunked by topic. Update SKILL.md to point to it.

  6. Restart and test the positive case

    command/clear

    Then send a real request that should trigger it, phrased the way you'd naturally ask — not a copy of the trigger phrase itself.

    Expected: Claude opens the skill body without you naming it explicitly.

  7. Test the negative case too

    Send an unrelated request in the same session and confirm the skill does not fire. A skill that over-triggers on loosely related requests is as much a problem as one that never fires — narrow the description if it does.

  8. Live with it for a week, then revisit

    Note every time it should have fired and didn't, or fired when it shouldn't have. Fold those cases back into the description and examples rather than patching around them in conversation each time.

Certification Prep — Can You Answer These?

  • A SKILL.md never fires even though its instructions look correct. What's the most likely cause?
    A: The description field — it's the trigger, not documentation. A vague or third-person-missing description is the single most common reason a skill never matches a request.
  • Why don't files inside references/ cost context if the skill never uses them?
    A: Skills use two-tier loading: only the short description is loaded at session start. The body and any references/ files load only when Claude actually opens them for a matching task — unused bundled content has zero context penalty.
  • When should logic live in scripts/ instead of just being described in the SKILL.md body?
    A: When the same code would otherwise be regenerated repeatedly, or when deterministic reliability matters more than flexibility — a script is token-efficient and doesn't vary run to run.
  • What's the difference in reach between a personal skill and a project skill?
    A: A personal skill (~/.claude/skills/) only helps you, across your own projects. A project skill (.claude/skills/, committed to git) helps everyone who clones that repository.

Part 03 · Extensibility

Commands

The simplest reusable unit — a saved prompt you type explicitly, with no auto-triggering.

Theory

A custom command is a single markdown file whose filename becomes the slash command. Drop review.md into .claude/commands/ and you get /review — no directory structure, no frontmatter required, just the prompt text as the file body.

The key mechanical difference from a skill: a command is always manually typed. It never auto-fires from a description match. That makes it the right tool for a prompt you want full deliberate control over invoking — versus a skill, which you want Claude to reach for on its own.

Two features make commands genuinely dynamic rather than static text: $ARGUMENTS captures anything typed after the command name, and a leading ! runs a shell command inline and injects its live output into the prompt — e.g. pulling the actual staged git diff into a review command.

Note: commands have effectively merged into skills in recent Claude Code versions — if a skill and a command share a name, the skill wins. For anything beyond a one-off saved prompt, build it as a skill instead.

A command is always typed explicitly — never auto-triggered

Key Takeaways

  • Manual invocation is the whole point — a command never fires on its own; that's what makes it the right tool when you want full deliberate control over exactly when something runs
  • ! shell injection turns a static prompt into a live one — the difference between "review my code" and "here is my actual staged diff, review it"
  • allowed-tools scopes what a command can touch — a review command that can only Read and diff can't accidentally become a command that edits your code
  • Commands are the on-ramp, skills are the destination — once you need auto-triggering or bundled reference material, you've outgrown a command

Hands-On

  1. Scaffold the folder

    commandmkdir -p .claude/commands

  2. Ask Claude to write a real one

    promptCreate a slash command /review in .claude/commands/review.md. It should inject the staged git diff via shell injection, then ask for a structured review covering code quality, security, and test coverage.

  3. Test it on a real diff

    Stage a real change first (git add), then run:

    command/review
    Expected: the actual staged diff appears inline in the prompt, followed by a structured review — not a generic "please share your diff" response.

  4. Add an argument-driven one

    promptCreate /fix-issue in .claude/commands/fix-issue.md that takes an issue number as $ARGUMENTS and investigates + fixes that GitHub issue.
    usage/fix-issue 123

  5. Restrict its tools

    Edit the frontmatter so /review can only read and diff, never edit — a review command shouldn't be able to silently change your code:

    frontmatter additionallowed-tools: Read, Grep, Bash(git diff:*)

  6. Namespace it for a team

    Move it to .claude/commands/dev/review.md and confirm it now runs as /dev:review — this is how a growing command library stays organized across a team.

Certification Prep — Can You Answer These?

  • Can a command auto-trigger the way a skill can?
    A: No. A command is always manually typed — that's the defining mechanical difference from a skill, which can fire automatically on a description match.
  • What does the ! syntax do inside a command file, and why does it matter?
    A: It runs a shell command inline and injects its live output into the prompt — e.g. pulling the actual staged git diff into a review command, rather than asking Claude to guess or ask for it.
  • If .claude/commands/review.md and .claude/skills/review/SKILL.md both exist, which one runs when you type /review?
    A: The skill. Commands and skills have been merged in recent Claude Code versions, and on a name collision, the skill takes precedence.

Part 04 · Extensibility

Subagents

Isolated, specialized workers with their own context window and restricted toolset.

Theory

A subagent is a fresh Claude Code instance with a pre-baked system prompt, a restricted set of tools, and its own separate context window — spawned by your main session to handle a focused subtask, then reporting back only the result. It has no memory of past invocations and no visibility into the main session's chat history: every call is a clean slate.

This isolation is the entire point. Delegating a noisy task (exploring dozens of files, running a verbose test suite) to a subagent keeps that noise out of your main conversation — the main session only sees the concise summary that comes back. Subagents cannot spawn further subagents, so delegation never nests more than one level deep.

Routing happens two ways: automatically, when your request matches the subagent's description field, or explicitly, by naming it ("use the code-reviewer subagent to..."). Explicit invocation is more deterministic and is what production workflows tend to rely on.

Subagents can run in parallel; each reports back only its concise result — one level deep, never nested

Key Takeaways

  • Isolation is the feature, not a side effect — a subagent's separate context window is what keeps noisy exploration from bloating your main conversation, not just an implementation detail
  • The description field routes work, exactly like a skill's does — "reviews code for security issues before commits" routes reliably; "security expert" doesn't
  • One level deep is a hard ceiling, not a current limitation — subagents cannot spawn subagents, so design your delegation tree assuming it never nests further
  • Model choice is a lever most people forget — a read-only exploratory subagent pinned to a fast model is both cheaper and quicker, with no quality cost for that kind of task
  • Explicit invocation beats automatic for anything you'll rely on repeatedly — naming the subagent is deterministic; hoping the description matches isn't

Hands-On

  1. Create one interactively

    command/agents

    Describe: "a code-reviewer subagent that checks diffs for security and style issues, with read-only tools."

  2. Inspect and tighten it

    Open .claude/agents/code-reviewer.md and sharpen the description field — this is what drives auto-routing.

  3. Invoke it explicitly

    promptUse the code-reviewer subagent to review my staged changes.

  4. Test automatic routing

    promptReview my changes before I commit.

    See whether it routes to the subagent on its own — if not, your description needs sharper trigger language.

    Expected: the response shows the subagent being invoked (a separate, labeled sub-task), not the main session doing the review itself.

  5. Build a second, cheaper subagent

    promptCreate a test-runner subagent, pinned to a fast/cheap model, that only runs the test suite and reports pass/fail plus failing test names — no analysis.

  6. Chain them sequentially

    promptUse the test-runner subagent to run the suite, then use the code-reviewer subagent to review any files touched by failing tests.

    This is the sequential pattern from the theory — output from one subagent feeding the next.

  7. Try a parallel fan-out

    promptSpawn three subagents in parallel to explore how authentication, billing, and logging are each implemented in this codebase, then summarize all three findings together.
    Expected: three separate concise summaries returned and synthesized — not three full explorations dumped into your main context.

Certification Prep — Can You Answer These?

  • Why does a subagent's isolated context matter, beyond just "organization"?
    A: It prevents a noisy task (exploring dozens of files, verbose test output) from bloating the main session's context — the main conversation only ever sees the subagent's concise final result.
  • Can subagent A spawn subagent B, which spawns subagent C?
    A: No — subagents cannot spawn further subagents. Delegation is always exactly one level deep from the main session.
  • What field determines whether a subagent gets auto-routed to for a given request?
    A: The description field — the same mechanism as skills. A specific, trigger-focused description routes reliably; a vague capability summary doesn't.
  • When is explicit invocation preferred over letting Claude auto-route to a subagent?
    A: In production or repeatable workflows, where you want deterministic behavior rather than depending on the description matching correctly every time.

Part 05 · Extensibility (experimental)

Agent Teams

Multiple full Claude Code sessions running in parallel, coordinating through a shared task list and direct messaging.

Theory

Agent Teams is an experimental, opt-in feature that goes a step further than subagents: instead of one session delegating to isolated helpers that only report back, a team lead spawns several teammates, each a full Claude Code session with its own context window, and they communicate directly with each other through a mailbox-style messaging system — not just back through the lead.

The team shares a live task list, so each teammate can see what's already claimed and avoid stepping on the same files. The lead's job is to break work into independent chunks, assign them, and synthesize the results once everyone's done.

This is genuinely different from subagents in kind, not just degree — and it costs more (tokens scale with the number of parallel sessions, each re-reading its own system prompt and context). Reach for it only when the work is too large for one context window and has real independent workstreams — a new feature touching UI, API, and DB schema simultaneously is the textbook case. For sequential or tightly-dependent work, it adds coordination overhead for no benefit.

Peer-to-peer messaging + a shared task list — the key difference from subagents, which only report to the lead
Experimental: disabled by default, and has known limitations around session resumption and shutdown behavior. Treat this as an advanced, occasional tool — not a daily default.

Key Takeaways

  • Peer-to-peer messaging is the actual innovation — subagents already gave you parallelism; what teams add is teammates talking directly to each other instead of routing everything through you
  • More parallelism means more token cost, not less — each teammate re-reads its own system prompt and context, so the speed gain trades directly against spend
  • The right question isn't "could this be a team" but "are these workstreams truly independent" — sequential or tightly-coupled work gets worse, not better, with team overhead
  • Experimental means real limitations, not just a label — session resumption and shutdown behavior have known rough edges; treat it as an occasional tool, not a daily default

  3. Observe coordination

Hooks

Deterministic automation — shell commands that fire on lifecycle events, independent of what the model decides to do.

Theory

Everything covered so far (skills, commands, subagents) is still the model deciding what to do. Hooks are different: they're deterministic shell commands (or HTTP calls, or prompts) that fire automatically at fixed points in the session lifecycle — regardless of what Claude "chooses." That guarantee is the whole point: a formatter that runs after every edit doesn't depend on the model remembering to run it.

A hook is defined by three parts: the event (when it fires — PreToolUse, PostToolUse, SessionStart, Stop, and others), an optional matcher (a regex filtering which tool calls qualify, e.g. only Write|Edit), and the handler itself.

PreToolUse hooks are special: they can inspect the actual command about to run and block it (exit code 2, or a JSON deny decision) — this is a real enforcement mechanism, going further than the static permission patterns from Part 1, which only match by pattern rather than by runtime inspection.

A PreToolUse hook can also short-circuit this chain with a deny decision, blocking the tool call outright

Key Takeaways

  • Hooks don't depend on the model remembering anything — that's the entire value proposition over "just ask Claude to always format after editing," which works until the one time it doesn't
  • PreToolUse is the only event that can actually stop something — most hooks observe and react after the fact; PreToolUse can inspect and block before a tool call ever runs
  • A matcher is a precision tool, not an afterthought — "Write|Edit" versus a bare wildcard is the difference between a hook that helps and one that fires constantly for no reason
  • Hooks compose with everything else you've built — the same guard that blocks a dangerous Bash call applies whether the command came from you, a skill, or a subagent

Hands-On

  1. Ask Claude to write your first hook

    promptAdd a PostToolUse hook to .claude/settings.json that runs prettier on any file after a Write or Edit tool call.

  2. Review before approving

    Read the generated JSON — check the matcher and the exact command — before letting it write to settings.json.

  3. Confirm it fires

    promptMake a small, deliberately unformatted edit to any file.

    Check that the file comes out auto-formatted afterward.

  4. Add a safety guard

    promptAdd a PreToolUse hook that blocks any Bash command containing "rm -rf".
    Expected: attempting a command containing that string gets refused before it runs, with a clear reason shown.

  5. Verify the guard actually blocks

    promptRun: rm -rf ./some-test-folder

    Confirm Claude reports the command was blocked by the hook rather than asking you to approve it — that distinction (blocked vs. merely flagged) is the whole point of PreToolUse.

  6. Add a SessionStart hook

    promptAdd a SessionStart hook that prints the output of "git status" and "git log -3 --oneline" so every new session opens with recent context already visible.

Certification Prep — Can You Answer These?

  • What fundamentally distinguishes a hook from a skill or a subagent?
    A: A hook is deterministic — it fires the same way every time an event and matcher condition are met, regardless of what the model decides. Skills and subagents are still the model choosing to act.
  • Which hook event can actually prevent a tool call from running, and how?
    A: PreToolUse — it can return exit code 2 or a JSON deny decision to block the tool call before it executes, unlike PostToolUse which only reacts after the fact.
  • What does the matcher field do in a hook definition?
    A: It's a regex filter that narrows which tool calls trigger the hook — e.g. matching only Write|Edit so a formatting hook doesn't fire on every single tool use.

Config Deep-Dive

The settings.json system underneath permissions, hooks, and MCP — scopes, precedence, and the fields worth knowing.

Theory

Claude Code reads configuration from up to five sources and merges them. Understanding the precedence order is what explains "why does my teammate's Claude Code behave differently from mine" — almost always the answer is a settings file at a different scope.

From highest to lowest priority: managed settings (deployed by an org's IT/security team — cannot be overridden by anything, including CLI flags), then CLI flags, then local (.claude/settings.local.json, personal, gitignored), then project (.claude/settings.json, committed and shared), then user (~/.claude/settings.json, your personal baseline across all projects).

One important exception: permission rules (allow/deny/ask) don't strictly override across scopes — a deny rule from managed settings and an allow rule in your local settings both apply, and deny wins the conflict, rather than one scope silently discarding the other's rule.

Managed settings can't be overridden by anything below — permission allow/deny is the one exception that layers instead of overriding

Key Takeaways

  • "Why does my teammate's Claude Code behave differently" almost always traces to scope — someone has a setting at a different precedence level, not a different version
  • Managed settings exist so an org can enforce a rule nobody can quietly override — not even from the command line, which is precisely the point when the rule is a security boundary
  • Permission rules are the one place precedence doesn't simply override — a deny from managed and an allow from local both apply, and deny wins; every other key follows strict higher-scope-wins
  • A pattern's specificity is a security decision — Bash(npm run test:*) is a scoped tool; Bash(*) is your entire shell handed over

Hands-On

  2. Compare your two active files

    Expected: your sessions use the override; a teammate without this file still gets the project default.

  4. Validate JSON syntax

    commandpython3 -m json.tool .claude/settings.json

  5. Write a real permission rule, not a toy one

    promptAdd a permission rule to .claude/settings.json that allows npm run test and its variants (test:unit, test:watch) but not npm run deploy, and denies Read access to the .env file entirely.

    Set the same key (e.g. model) to two different values — once in ~/.claude/settings.json, once in .claude/settings.json — start a session, and confirm which one actually won. This is the fastest way to internalize the precedence order for good.

MCP Servers

Connecting Claude Code to tools and data beyond your local filesystem.

Theory

Model Context Protocol (MCP) servers give Claude Code tools it doesn't have out of the box — talking to GitHub, Linear, Sentry, a Postgres database, Figma, or an internal API. Once connected, the server's tools show up alongside Claude's built-in ones (Read, Bash, Edit) and get invoked the same way.

Servers are added with claude mcp add, and live at one of four scopes — local (personal, default), project (.mcp.json, committed and shared with the team), user (all your projects), or managed (enterprise allowlist/denylist). Hosted services typically use OAuth: you add the URL, then complete a browser sign-in via /mcp inside a session.

The team pattern that actually works: commit a shared .mcp.json listing which servers the project uses, and let each developer supply their own auth tokens through personal, local-scoped config — so the server list is consistent but credentials never end up in git.

Once connected, MCP tools are invoked exactly like built-in ones — Read, Bash, and github_create_pr sit side by side

Key Takeaways

  • MCP turns Claude Code from an editor into an execution agent — the difference between "read my code" and "go check Sentry, then file the Jira ticket"
  • Tools are indistinguishable once connected — an MCP tool call looks and behaves exactly like Read or Bash to Claude; there's no second-class status
  • Scope is a security decision, not a convenience setting — project-scoped .mcp.json ships the server list, but credentials must stay local or you've committed a secret
  • OAuth servers don't need you to manage tokens — /mcp handles the browser sign-in flow; you never touch a key by hand
  • More connected servers = more standing context cost — every tool definition loads at session start, so disconnect what you're not using

Hands-On

  1. Connect a no-auth server first

    commandclaude mcp add --transport http claude-code-docs https://code.claude.com/docs/mcp

    This is a hosted, read-only server with full-text search over the Claude Code docs — safe to test the whole flow before touching anything with write access.

  2. Verify the connection

    command/mcp
    Expected: claude-code-docs shows as connected, with no auth warning next to it.

  3. Use it for something you'd otherwise have to search for

    promptWhat does the Claude Code docs say about CLAUDE.md size limits, and what does /doctor do about it?

    Confirm the answer cites the actual doc content rather than Claude's general knowledge — that's the tool call actually firing.

  4. Add one that needs real auth

    commandclaude mcp add --transport http github https://api.githubcopilot.com/mcp/

    Complete the OAuth flow via /mcp, then try:

    promptReview open PR #<number> and suggest improvements.

  5. Set up the team pattern for real

    Create a project-root .mcp.json listing the GitHub server (no token in it), commit it, and confirm a fresh clone shows the server as "needs authentication" rather than already connected.

  6. Audit and prune

    command/mcp

    Disconnect any server you added just to test but don't actually use day to day — every connected server is standing context cost on every future session.

Certification Prep — Can You Answer These?

  • What's the practical difference between a local, project, and managed-scope MCP server?
    A: Local is personal and default; project (.mcp.json) is committed and shared with the team; managed is enterprise-enforced via an allowlist/denylist that individuals can't override.
  • Why shouldn't you put an auth token directly in a committed .mcp.json?
    A: The file is shared via git — a token in it leaks to everyone with repo access. Tokens belong in personal, local-scoped config even when the server list itself is shared.
  • How does Claude Code complete authentication for a hosted MCP server like Sentry or GitHub?
    A: Via the /mcp command, which triggers a browser-based OAuth sign-in flow — you never manually paste or manage a token for these.
  • What's a real cost of connecting many MCP servers, even ones you rarely use?
    A: Every connected server's tool definitions load into context at session start, adding standing token cost whether or not you use them that session.

Feeding it a Knowledge Base

Huge doc sets, coding guidelines, and specs — without paying their token cost on every single turn.

Theory

This is where Part 2's two-tier loading model (Part 2) gets used deliberately for a real team problem. CLAUDE.md is loaded on every single turn — so it must stay short and durable, holding only the guidelines that should always apply. Everything else — an entire API spec, a 200-page domain document, your full coding-standards doc, database schemas, compliance policy — belongs in a skill's references/ folder, where it costs nothing until Claude actually opens it.

The practical shape: create a skill whose job is "know this domain" (e.g. payments-domain). Its SKILL.md body stays short — a description, and a map of what's inside references/ and when to open which file. The bulk documents live as separate, logically-chunked files, not one giant blob — chunking by topic means Claude only pulls in what's relevant to the actual question.

For genuinely huge codebases, the same idea scales down to the directory level: path-scoped skills nested inside subsystems (packages/api/.claude/skills/) fire only when Claude is working in that specific area, paired with a hierarchical CLAUDE.md per subsystem.

The size of the box on the right is unlimited in practice — none of it costs context until opened
The one mistake that defeats this: pasting a raw giant document directly into SKILL.md itself instead of a references/ file. That reintroduces the always-loaded cost you were trying to avoid.

Key Takeaways

  • Every turn pays for CLAUDE.md — so its real budget isn't "how much can I fit," it's "what's worth spending tokens on 100% of the time"
  • references/ is free until read — this single fact is why you can bundle an entire spec library into a skill with zero idle cost
  • Chunking is a retrieval decision, not tidiness — one giant reference file forces Claude to pull in everything even for a narrow question; ten small ones let it grab only what's relevant
  • SKILL.md becomes a table of contents, not a manual — its only job is telling Claude which reference file answers which kind of question
  • Path-scoping is the same idea at repo scale — conventions that only apply to one subsystem shouldn't load for every other subsystem either

Hands-On

  1. Pick a real large document

    A schema doc, a style guide, a spec, an onboarding wiki page — something you actually have lying around, not a toy example.

  2. Create the domain skill

  3. Ask Claude to organize it — don't do the chunking yourself

    promptTake this document [paste/point to it] and split it into logically-chunked files inside .claude/skills/my-domain/references/, one file per major topic. Then write a short SKILL.md whose body maps each reference file to the kind of question it answers.

  4. Test targeted retrieval

    Ask a question that should only need one chunk, and confirm Claude opens just that file rather than everything.

    Expected: the response cites content specific to one reference file, and you can see only that file was read (not the whole references/ folder).

  5. Deliberately break the anti-pattern, then fix it

    Paste the raw document straight into SKILL.md itself instead. Notice it now loads on every session start regardless of relevance — then move it back to references/ and confirm the cost disappears.

  6. Scale it down to a subsystem

    If you work in a monorepo, create one path-scoped skill (e.g. packages/api/.claude/skills/api-conventions/) and confirm it only fires when you're actually editing files in that package.

Other Important Concepts

Session mechanics that change how you operate day to day — plan mode, checkpoints, headless scripting, and memory nuances.

Theory

Plan mode puts Claude into read-only exploration — it investigates and proposes a plan without editing anything. Toggle with Shift+Tab, /plan, or --permission-mode plan. Use it before anything expensive to get wrong: migrations, auth, payments, multi-file features.

Every plan (and every edit) creates a checkpoint you can rewind to with Esc Esc if the implementation goes sideways — cheaper than manually undoing a bad multi-file change.

Context management goes beyond /compact: /context reports current usage so you compact by choice, not surprise. Your project-root CLAUDE.md survives compaction — it's re-read from disk afterward.

Headless mode (-p/--print) is the same agent with the UI stripped out — this is literally what runs inside the GitHub Actions/GitLab CI integration from Part 1. --output-format json, --allowedTools, and --max-turns make it scriptable and boundable for unattended runs.

On memory: @path imports inside CLAUDE.md organize a large file but do not reduce its context cost — imported content still loads at launch. The actual lever for reducing always-on cost is a path-scoped rule (.claude/rules/*.md with a paths: field), which only loads when Claude touches a matching file.

Plan mode + checkpoints give you a review gate on the way in, and a cheap undo on the way out

Key Takeaways

  • Plan mode turns "hope it does the right thing" into "review the plan first" — read-only exploration before a single file changes, for anything expensive to get wrong
  • Checkpoints make experimentation cheap — a bad multi-file edit is one Esc Esc away from undone, so you can try the riskier approach without dreading the cleanup
  • @path imports are organization, not optimization — the actual context-reducing lever is a path-scoped rule, which only loads for matching files; imports just tidy up a big CLAUDE.md that still loads in full
  • Headless mode is the same agent, not a lesser one — -p runs the identical agent loop with the UI stripped out, which is exactly what your CI pipeline is doing under the hood
  • Git worktrees are the lightweight parallelism option — reach for one before reaching for a full Agent Team when you just need one more isolated lane of work

Concept 03 · Deep Dive

Claude Code Config

The mechanics underneath CLAUDE.md, commands, skills, and rules — where instructions actually live, who can load them, and why. This deepens Parts 1, 2, 3, 9, and 11 rather than repeating them; each subsection says what's new here versus what those parts already covered.

3.1

The three memory levels, and the version control boundary between them

Claude Code assembles instructions from three levels at session start: user memory (~/.claude/CLAUDE.md), project memory (repo/CLAUDE.md), and directory memory (a nested CLAUDE.md closer to the files you're working on). Part 1 already covers running /init to generate the project file — what's new here is the boundary that runs between these three levels: only two of them are inside the repository. Version control is that boundary. A teammate who clones the repo gets the project and directory files. They get nothing of your user-level file, because it never lived in the repo to begin with.

This produces a specific, silent failure: you teach Claude Code a convention on your machine, it holds for a week, a new engineer clones the same repository and gets none of it. Nothing regressed and nothing errored — the instruction simply never traveled, because it was never committed. The fix is a placement discipline, not a debugging step: anything the whole team needs to be true goes in the repo; anything that's just your personal habit stays in your user file.

Only the two committed files reach another engineer's machine — and the failure when they don't is completely silent
3.2

@import and .claude/rules/ as two ways to split a long file, and /memory to check what actually loaded

A project file that starts at twenty lines rarely stays there — a year in, it's covering the build system, test conventions, API style, and a deploy checklist all at once. Two problems follow: reviewers stop reading it, and every line loads into every session regardless of relevance (Part 9 covers the token-cost side of this; this is the organizational side). There are two ways to split it. @import pulls another file in at the point where the line appears — @./docs/conventions/testing.md — keeping the root file short while the same document also serves as a readable onboarding guide. The catch: an import is only as shared as the file it points at. Import a path outside the repo and that section silently disappears for anyone else.

The second way is .claude/rules/ — a directory of small files instead of one document with headings. Each file covers one subject, gets reviewed on its own in a pull request, and can carry YAML frontmatter that decides when it loads (see 3.4). When behavior differs between two engineers on the same repo, the fastest diagnostic is the /memory command — it lists exactly which memory files loaded for the current session, before you reword anything or start guessing.

An import is only as shared as the file it points at — the uncommitted one silently vanishes for everyone else
3.3

Commands in project vs. user scope, and the SKILL.md frontmatter fields that change behavior

Part 3 covers what a command is; the piece worth adding is scope. A command at .claude/commands/release-notes.md (project scope, committed) reaches every engineer who clones the repo. One at ~/.claude/commands/summarize-paper.md (user scope) never reaches a teammate — it's yours, in every project, on this machine. The rule: team workflow → project scope; personal habit → user scope. The property that separates any command or skill from a memory file: it isn't loaded until you invoke it, where a memory file is in context from the first token of the session whether it's relevant or not.

Beyond name and description (Part 2), four SKILL.md frontmatter fields do real work: argument-hint tells the caller what to pass, so it reads like "[schema name]" rather than a vague sentence; allowed-tools is a structural limit — a skill without Write in that list cannot write, full stop, no matter what its body says; and context: fork runs the skill as an isolated subagent (Part 4's isolation model, applied to a skill instead of a delegated task) — the intermediate work stays in the fork and only the findings return, instead of forty tool calls' worth of raw dumps competing for attention in your main conversation.

Three homes for an instruction, distinguished by who pulls it in — only the skill can restrict its own tools and isolate its own context
3.4

Path-scoped rules: why a glob beats a directory file when a convention follows a file type

Part 11 introduced path-scoped rules; here's the mechanical reason to prefer them over nested directory CLAUDE.md files for a specific class of convention. A directory file scopes by folder — everything under src/billing/ gets the same rules, whether it's invoice.ts or invoice.test.ts. A rule with a paths: glob in its frontmatter (.claude/rules/tests.md with paths: ["**/*.test.ts"]) scopes by file pattern instead — it follows your test files into src/billing/, src/auth/, and a module added next week that nobody remembered to update.

Some conventions genuinely are folder-shaped (everything in services/billing/ uses a different currency library) — that's still a directory file's job. But a convention that tracks a file type rather than a file location — test files, migration files, anything matching *.spec.ts — belongs in a glob-scoped rule, or it silently misses every new folder that convention should have applied to.

The rule loads on the file it matches, not the folder it sits in — that's the whole advantage
3.5

Plan mode vs. direct execution: choosing, and pairing with the Explore subagent

Part 11 covers what plan mode is; the piece worth adding is when to reach for it. The test isn't the size of the request — it's whether a design decision exists at all. If more than one reasonable approach exists, or the change touches many files or sets a pattern others will copy, use plan mode: it explores read-only and produces a written plan, and reversal costs one sentence if you don't like it. Direct execution reverses a wrong design by re-reading a forty-file diff and reverting everything — the trade isn't safety versus speed, it's where the review happens: before the work, on a description, or after it, on a diff.

Plan mode pairs naturally with the built-in Explore subagent (Part 1.2/4's isolation model again): Explore gathers — greps, reads forty files, returns findings, not raw matches — and the main session decides, writing the plan from those findings without the intermediate grep output ever cluttering the conversation that has to hold the decision.

The cost of being wrong decides the mode, not the size of the request
3.6

Iterative refinement: worked examples, test-driven loops, the interview pattern, and batching feedback

Four patterns consistently improve output quality, and none of them require new mechanics — just a different way of prompting. Worked examples: show one input/output pair before asking for the real thing, the same multishot principle from general prompt engineering, applied to a coding task. Test-driven loops: hand Claude a failing test and the instruction not to edit it — the test then encodes what "done" means independently of whatever the code happens to do, closing the loop with a signal Claude can check without you. The interview pattern: for an ambiguous request, ask Claude to ask clarifying questions before writing anything, rather than guessing and correcting later. Batching feedback: give every correction in one message rather than one round-trip per issue — Claude fixes all of them against a stable target instead of re-solving a moving one.

The common thread: in each pattern, you're handing the agent a better signal to iterate against — a concrete example, a failing assertion, an explicit question, or a complete list of what's wrong — rather than a vaguer instruction it has to interpret and often re-interpret across several turns.

Test-driven iteration closes the loop without you — the most useful thing you can hand an agent is a signal it can check on its own
3.7

Non-interactive runs, structured output, and why a fresh instance reviews your code better

Part 11 covers -p and --output-format json for headless mode; one flag worth adding is --json-schema, which constrains the response to a schema you supply — the validated result lands in a structured_output field, so a downstream script can consume it without a parsing step that might fail on a slightly-off response shape.

Separately — and this applies whether you're headless or interactive — a Claude session that just spent tens of thousands of tokens implementing a feature is a biased reviewer of that same feature: it knows why every decision was made, because it made them, and asking it to review its own work tends to produce polite agreement and minor nit-picks. A fresh session with none of that history reads the code cold and flags what looks odd exactly like a colleague who wasn't in the original conversation. This is the same context-boundary principle from 1.2 and 1.7, applied to code review specifically: close the implementation session, start a new one, and review from there.

Same self-review bias humans have — a fresh reviewer with none of the writer's context catches more, not less

Concept 04 · Reliability

Prompting and Output

Making output you can parse, and output you can trust — and knowing which of those two problems a prompt can actually solve. Most mistakes here are a prompt offered as the fix for something only a schema or a validator can fix.

4.1

Explicit criteria, not vague confidence language

A common failure: Claude reviews pull requests in CI, developers read the first few comments, find half are wrong, and stop reading. The instinct is to patch the prompt — "be conservative, only flag issues you're confident about." It doesn't work, because a disposition is not a rule. "Be conservative" names an attitude with no calibrated threshold behind it — the model has nothing to check itself against, so what actually shifts is the wording ("this may be a potential concern" instead of "this is a bug"), not the set of things flagged.

A criterion, by contrast, is a statement about the input that's true or false and that a reader could verify themselves: "flag only when the value reaches a SQL sink and originates from a request parameter and no escaping appears on any path between them." Writing the exclusions down explicitly (test fixtures, already-escaped values) removes whole families of false positives at once — cheaper than any amount of "be more careful." And asking the model to emit its trigger alongside each finding — which line, which sink, which pattern — turns "some of these are wrong" into "one specific rule is wrong," which is fixable.

A disposition cannot be tested; a criterion can — that difference is the whole mechanism
The trust math: 18 comments at 8-correct/10-wrong (44% precision) trains developers to stop reading within two weeks — even though it caught more real bugs than 6 comments at 5-correct/1-wrong (83% precision) did. Raw recall isn't value; value is findings that get acted on. Optimize precision first in an automated review setting, even at a visible cost in recall — you can raise recall later, once the channel is trusted enough to be read.
4.2

Few-shot examples: what they fix, how many, and why they generalize

A few-shot example is an input paired with the output you wanted, placed in the prompt before the real input — nothing is trained, the examples are just tokens the model conditions on. Few-shot's strongest use is making output shape consistent: dates as YYYY-MM-DD, an empty list instead of the string "none," keys in a fixed order. Two well-chosen examples beat three paragraphs describing the format, because a described format has to be interpreted while an example of the format simply is the format.

Its second job is resolving ambiguity that's hard to write as a rule — which of two numbers on an invoice is the "real" total, when the boundary depends on layout rather than a clean rule. One example showing the choice plus one sentence of reasoning teaches the underlying rule, not just the answer; an example with only input→output teaches a lookup, which won't transfer to a new layout. This is why count matters less than people assume: few-shot enables generalization, not lookup. Twenty ordinary examples spend context restating what the model already handles. Two to four examples picked at the genuine boundary — cases a reasonable person could go either way on — raise the ceiling further than twenty easy ones ever will.

Two examples doing two different jobs — only the second one (with reasoning) teaches a rule that transfers
What few-shot doesn't fix: it won't put a fact into the output that wasn't in the input, won't make arithmetic reliable, and won't guarantee the response is parseable at all — format inside a valid response and the existence of a valid response are two different problems. The second belongs to 4.3.
4.3

Structured output through tool_use and JSON Schema

Asking in prose ("respond with JSON matching this shape") works most of the time and fails in irritating, non-semantic ways: a markdown fence, a sentence of preamble, a trailing comma — failures in the transport, not mistakes about the content. The reliable path is defining a tool whose only purpose is to receive the extracted data, with an input_schema, passed in the tools array. The model returns a tool_use block whose input is already a parsed object of the declared shape — no fence to strip, no brace to find.

The single most tested idea here: a schema removes syntax errors, not semantic errors. It guarantees stated_total is a number and invoice_number is present. It cannot guarantee the number is the right number — if the page says 1,240.00 and the model reads 1,204.00, the response is valid JSON, fully schema-conformant, and wrong. A schema moves you from two classes of failure to one; that's a real gain, and it is not the whole job (4.4 is the rest). One useful pattern: ask for the same quantity two ways — a stated_total read directly and a calculated_total derived by summing line items — so your own code can compare them and catch exactly the gap the schema can't see.

The mirror-image mistake is forcing a tool in a conversational agent: force lookup_order on every turn and the agent can no longer ask "which of your three orders do you mean?" — it calls the tool with a guessed ID instead.

Two more decisions worth making deliberately. Nullable beats optional for extraction: mark a field required with no possible answer and you've instructed the model to fabricate something. "type": ["string", "null"] lets it return a present null — positive evidence the field was considered and genuinely absent — versus leaving the key out entirely, which is ambiguous between "not applicable" and "the model forgot." And an enum needs an "other" branch with a free-text companion field — a closed enum doesn't prevent bad data, it just makes bad data unmeasurable; adding other plus the original wording gives the unmatched case somewhere to go, and is literally how you discover your next enum value from real data instead of guessing.

4.4

Validation and retry, and what retry cannot fix

The schema only checked structure — you still need a validation layer, running as your own code after the response, asserting what a schema can't express: calculated_total reconciles with stated_total within a cent, issue_date is a real date not in the future, payment_terms_detail is non-null whenever payment_terms is "other". When a check fails, a bare retry with the same prompt is close to a no-op — you gave the model no new information. What works is retrying with the specific failure appended: "calculated_total (91.00) does not match stated_total (100.00)" gives the model a pointer to exactly where the output was inconsistent, and recovers a large share of arithmetic slips and misread digits, because the correct information was in the source document all along.

That clause — information that was in the source — is the boundary retry cannot cross. If the PO number is genuinely obscured by a stain, three retries don't recover it; each one just burns tokens and pushes the model harder toward inventing something plausible. The retry policy has to distinguish these two cases explicitly, and cap attempts at two or three as a hard stop, not a hope. Routing to a human queue isn't the failure case — it's a designed outcome, and it needs to carry which field is missing, what the model saw instead, and which check rejected it, or the human starts back at square one. This is also where a detected_pattern tag (from 4.1) earns its keep on the failure side too: without it you know a finding was wrong; with it you know which rule was wrong.

The decision that matters is the second diamond, not the loop — more retries against missing evidence only raise the odds of a confident invention
4.5

The Message Batches API and its tradeoffs

Everything above assumed a request you wait on. The Batches API submits many independent requests as one job, processed asynchronously, results collected when it finishes. Four properties decide every question about it: roughly half the cost of the same requests sent synchronously; up to 24 hours to complete with no latency guarantee inside that window — a batch may return in ten minutes or in twenty; each entry is a single message request, not a multi-turn agentic loop; and a custom_id you set travels with each request and returns on its result, with results not guaranteed to come back in order.

An overnight audit of ten thousand archived invoices — nobody waiting, each document independent, no tool loop — is exactly what batching is for. An automated review that must post before a PR can merge is exactly what it isn't: a developer is watching, and a job with no latency guarantee and a 24-hour ceiling can't sit in that path however attractive the saving looks. The distinction worth holding onto: "nobody needs an answer within seconds" is not the same as "nobody has a deadline" — a report due at 9am has a deadline, and only fits batching because submission happens with hours of slack in front of it. Move the same job to 8am and the 24-hour window no longer fits inside the gap. Ask how much slack sits between submission and when the result is needed, not how patient the reader feels.

The saving is real; the cost of missing the deadline is total — decide who's waiting first, price second
4.6

Multi-instance and multi-pass review

Ask Claude to write a module, then in the same session ask it to review what it just wrote — it reports the code looks correct, more often than you'd like, and the reason is structural, not a tone problem. Every assumption the generator made is still in context, presented as established fact. If it decided the input list is always non-empty, that decision sits in the transcript and the review pass reads it as background rather than the thing to test — plus a weaker pull toward consistency, since agreeing with recent output is the path of least resistance. Instructing it to "review critically" doesn't remove the context — the assumptions are still there, still framed as settled; you change tone, not blind spots. Turning on extended thinking doesn't either — more reasoning over the same context explores that context more thoroughly, errors included; thinking helps with problems that need depth, not problems that need independence.

The actual remedy is a separate instance with a clean context — the code and the requirements, nothing about how the code came to be. This is the exact mechanism the Config tab's 3.7 already names for you: a fresh Claude Code session, or a spawned reviewer subagent, reading the work cold. A second, independent dimension is size: a 500-file review in one request suffers attention dilution — every file gets a slice of a fixed budget, and the specific detail noticed in file three is gone by file two hundred. The fix pairs a per-file pass (small enough to notice specifics) with one integration pass that reads only the per-file summaries, looking at seams — interface mismatches, a contract changed in one place and consumed in another — small enough to hold the whole picture, which is exactly the per-file-plus-integration pattern from Config 3.6, now applied to review instead of implementation.

In Claude Code this is a fresh session or a spawned reviewer subagent; in CI it's naturally a separate invocation

Key Takeaways

  • A disposition cannot be tested; a criterion can — "be conservative" gives the model no threshold to check itself against, while an explicit, checkable condition does the actual work "be careful" was supposed to
  • Precision, not recall, is what keeps an automated reviewer trusted — a reviewer wrong half the time gets treated as noise, and the correct findings go in the bin along with the wrong ones
  • Few-shot teaches a policy, not a lookup table — the reasoning sentence in an example is the part that transfers to an unseen input; the count matters far less than picking boundary cases
  • A JSON Schema is a syntax guarantee, not a truth guarantee — this is the single most tested idea in the whole domain, and the gap it leaves is exactly what validation exists to close
  • Nullable says "I looked and it's not there"; a missing key just says "maybe" — that ambiguity is why nullable beats optional for extraction specifically
  • Retry only recovers what the source actually contains — appending the specific error fixes arithmetic slips; it cannot recover a fact that was never in the document
  • Batching trades latency certainty for cost, full stop — the question isn't how patient your reader is, it's how much slack sits between submission and the moment the result is actually needed
  • A reviewer's independence comes from what it cannot see, not from being told to be harsher — same context in, same blind spots out, regardless of tone or thinking budget

  • Why does adding "be conservative, only flag high-confidence issues" to a prompt typically fail to reduce false positives?
    A: A disposition is not a rule — it names an attitude with no calibrated threshold. The model has nothing concrete to check itself against, so what shifts is the wording (more hedging), not the actual set of things flagged.
  • Why does an architect optimize for precision over recall in an automated code review setting, even at a visible cost in bugs caught?
    A: A reviewer wrong half the time gets treated as noise, and once that happens, the correct findings are discarded along with the incorrect ones — trust in the channel, once lost, costs more than the extra bugs caught by higher recall.
  • What's the difference between an example showing only input→output and one that adds a sentence of reasoning?
    A: Input→output alone tells the model what was chosen for that specific case (a lookup). Adding the reasoning tells the model the rule that produced the choice — and the rule, not the specific answer, is what generalizes to an unseen input.
  • A JSON Schema guarantees a response is syntactically valid. What can it never guarantee?
    A: That the values are semantically correct — a schema cannot express a cross-field constraint like "these two numbers must reconcile," so a response can be fully schema-conformant and still factually wrong.
  • When is forcing tool_choice to a specific named tool the right call, and when is it a mistake?
    A: Right for single-purpose extraction where prose is never a valid answer (e.g. batch document processing). A mistake in a conversational agent, where forcing a tool removes the model's ability to ask a clarifying question instead of guessing an argument.
  • Why is a nullable field usually better than an optional one for extraction tasks?
    A: A present null is positive evidence the model looked and found nothing. A missing key is ambiguous between "not applicable to this document" and "the model simply forgot" — nullable removes that ambiguity.
  • What class of validation failure can retry-with-error-appended actually fix, and what class can it never fix?
    A: It recovers failures where the correct information exists in the source but was misread (arithmetic slips, transposed digits) — the specific error gives the model something new to work with. It cannot recover a fact that was never in the source at all; more retries there just raise the odds of a confident fabrication.
  • Give an example of a workload that "fits batching well" and one that fails the test, and say why.
    A: A nightly regression report due at 9am fits — nobody is waiting, and there's slack between submission and deadline. A support conversation never fits — the customer is waiting in real time, and the work needs a tool result back before the next turn can even be decided.
  • Why doesn't asking the same session to "review your code as a harsh critic" fix the self-review bias?
    A: The generating session's assumptions are still present in context, still framed as settled fact rather than choices to test. A tone instruction changes the wording of the review, not what the model can and can't see — only a genuinely separate instance with a clean context removes the bias.
