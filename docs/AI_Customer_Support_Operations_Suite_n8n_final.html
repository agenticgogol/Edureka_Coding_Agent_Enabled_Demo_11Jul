Module 1

Automated Support-Ticket Pipeline

Build the same AI-assisted automation twice: first as an API-style webhook, then as a polished customer-facing n8n web form. The LLM classifies; deterministic code validates; the workflow owns routing.

Webhook + curln8n web formLLM classificationValidationUrgent/standard routingReceipts

Scenario and finished outcome

A customer submits a support issue. n8n creates a ticket ID, asks an LLM for a structured classification, safely parses and validates the response, and routes the ticket to either an urgent human-review queue or a standard queue. Build the API version first; after it passes its tests, duplicate it and replace the entry/exit experience with an n8n-hosted form.

Urgent example

{
  "customer_name": "Asha Rao",
  "email": "asha@example.com",
  "message": "I was charged twice for order ORD-1048 and the duplicate amount is still showing. Please refund it urgently."
}

Expected: payment_issue, urgent, requires_human=true, queue urgent-human-review.

Standard example

{
  "customer_name": "Rahul Sen",
  "email": "rahul@example.com",
  "message": "How can I update the delivery address for order ORD-2055? It has not shipped yet."
}

Expected: a non-urgent category, standard route, queue standard-support. Exact category wording may vary; the route must not.

Webhook version

POST Webhook→Normalize→Basic LLM Chain→Validate JSON→Switch→Edit Fields receipt

Web-form version

Form Trigger→Same classification pipeline→Switch→Branch receipt→Form Ending

Business rules

  • Categories: delivery_delay, payment_issue, refund_request, product_issue, account_issue, other.
  • Urgent: duplicate charge, suspected fraud, safety issue, account compromise, or explicit severe escalation.
  • The LLM may recommend a route, but the Code node constrains values and applies deterministic safety overrides.
  • No refund or external message is sent in Module 1.
Teaching point: The workflow—not the LLM—owns the control flow. This is AI-assisted automation, not an agent.

Part I — Build the working webhook version

1

Add and configure Webhook

From the blank canvas select Add first step → On webhook call. Set HTTP Method to POST, Path to support-ticket, and Respond to When Last Node Finishes. Keep Response Data as the first incoming item/JSON. This setting is essential for this lab because each Switch branch ends in an Edit Fields node.

Avoid the earlier error: do not choose “Using Respond to Webhook Node” unless you also add and connect that node. Otherwise n8n reports No Respond to Webhook node found in the workflow.
2

Add “Normalize Input” Code

Add a Code node. Keep “Run Once for Each Item”. Read from $json.body because Webhook wraps the request body. Validate that message and email exist; create a stable ticket ID.

const b = $json.body ?? $json;
if (!b.message || !b.email) throw new Error('email and message are required');
return { json: { ticket_id: `T-${Date.now()}`, customer_name: b.customer_name ?? 'Customer', email: b.email, message: b.message, created_at: new Date().toISOString() } };
3

Add Basic LLM Chain and choose the model

Click the plus after Normalize Input and add Basic LLM Chain. Set Prompt source to Define below and paste the prompt below. On the bottom model connector of the chain click +, choose OpenAI Chat Model, select your OpenAI credential, choose an inexpensive available chat model, and set Temperature to 0. The model is selected inside the Chat Model sub-node—not inside the Code or Webhook node.

Classify this customer support ticket. Return ONLY valid JSON with keys:
category, sentiment, priority, summary, requires_human, reason.
Allowed category: delivery_delay,payment_issue,refund_request,product_issue,account_issue,other.
Allowed priority: low,normal,high,urgent.
Ticket: {{ JSON.stringify($json) }}
4

Parse the LLM text and enforce safety rules

Run once and inspect the Basic LLM Chain output. It commonly returns a field named text containing JSON as a string. Add a Code node named exactly Validate Classification, keep Run Once for Each Item, and paste:

const raw = $json.text ?? $json.output ?? '';
let c;
try {
  c = JSON.parse(String(raw).replace(/```json|```/g, '').trim());
} catch {
  c = { category:'other', sentiment:'unknown', priority:'high',
        summary:String(raw), requires_human:true, reason:'Parser fallback' };
}

const original = $('Normalize Input').item.json;
const categories = ['delivery_delay','payment_issue','refund_request','product_issue','account_issue','other'];
const priorities = ['low','normal','high','urgent'];
if (!categories.includes(c.category)) c.category = 'other';
if (!priorities.includes(c.priority)) c.priority = 'normal';

if (/charged twice|duplicate charge|fraud|unsafe|danger|hacked|compromised/i.test(original.message)) {
  c.priority = 'urgent';
  c.requires_human = true;
}
return { json: { ...original, ...c } };

This converts the LLM string into real fields and preserves the ticket data. The deterministic override ensures known financial, security, and safety phrases cannot be under-prioritized by the model.

5

Add Switch

Add Switch, Mode: Rules. Value: {{ $json.priority }}. Create output 0 when equal to urgent; use fallback output for everything else.

6

Create complete branch receipts

From the urgent output add Edit Fields named Escalation Receipt. Leave Include Other Input Fields on and add: queue string urgent-human-review; status string escalated; sla_minutes number 15; human_review_required boolean true; customer_message string Your request has been escalated to our priority support team.

From the fallback output add Edit Fields named Standard Receipt. Keep input fields and add: queue=standard-support; status=received; sla_minutes=240; human_review_required=false; customer_message=Your support request has been received and added to our standard support queue.

7

Test with the Test URL

  1. Click Execute Workflow. The canvas should say it is waiting for the Test URL.
  2. Open Webhook, copy the Test URL, and paste it into the command below.
  3. Run the command once. Test webhooks normally accept one request per listening session; click Execute Workflow again before the next request.
curl -X POST 'PASTE_TEST_URL' \
  -H 'Content-Type: application/json' \
  -d '{
    "customer_name":"Asha Rao",
    "email":"asha@example.com",
    "message":"I was charged twice for order ORD-1048. Please help urgently."
  }'

The terminal should receive the final branch JSON, including ticket ID, category, priority, summary, queue and SLA.

8

Publish and use the Production URL

Save and publish/activate the workflow. Return to Webhook, select Production URL, and use that URL without first clicking Execute Workflow. Production executions are inspected from the Executions tab.

404 “webhook is not registered”: for a Test URL, click Execute Workflow first; for a Production URL, publish/activate the workflow. Also make sure the URL does not contain an accidental trailing backslash.

Acceptance test

  • Missing message produces a controlled error.
  • Duplicate-charge message is routed urgent even if the LLM under-classifies it.
  • Output includes ticket ID, category, priority, queue and summary.
  • No API key appears in execution data.

Download, import and convert

After import: imported credentials are never embedded. Re-select your OpenAI credential and a currently available model. If Switch rules render differently in your n8n release, recreate the urgent-equals rule and fallback in the UI.

3A — Create the order-details tool workflow

1

Create and name the workflow

2

Add the deterministic lookup

Add a Code node named Get Order Details, Mode Run Once for Each Item, Language JavaScript. Paste the lookup below. The final object is the response returned to the calling agent.

const orderId = $json.order_id;
const orders = {
  'ORD-1048': { customer_name:'Asha Rao', order_value:120, currency:'USD',
    product:'Wireless Headphones', order_status:'shipped',
    promised_date:'2026-09-10', shipped_date:'2026-09-07' },
  'ORD-2055': { customer_name:'Rahul Sen', order_value:75, currency:'USD',
    product:'Smart Speaker', order_status:'processing',
    promised_date:'2026-09-24', shipped_date:null }
};
if (!orders[orderId]) return { json:{ found:false, order_id:orderId, error:'ORDER_NOT_FOUND' } };

3C — Create the compensation calculator

1

Define two typed inputs

Create M3C — Calculate Compensation Tool. Add When Executed by Another Workflow, rename it Receive Compensation Inputs. Add required Number inputs order_value and delay_days.

2

Add Calculate Compensation

Add a Code node with this deterministic policy:

const orderValue = Number($json.order_value);
const delayDays = Number($json.delay_days);
if (!Number.isFinite(orderValue) || !Number.isFinite(delayDays))
  throw new Error('order_value and delay_days must be numbers');
let percentage = 0, eligible = false, requiresHumanReview = false;
if (delayDays >= 3 && delayDays <= 5) { percentage = 5; eligible = true; }
else if (delayDays >= 6 && delayDays <= 10) { percentage = 10; eligible = true; }
else if (delayDays > 10) { requiresHumanReview = true; }
const proposedAmount = Number((orderValue * percentage / 100).toFixed(2));
return { json:{ eligible, order_value:orderValue, delay_days:delayDays,
  percentage, proposed_amount:proposedAmount, currency:'USD',
  approval_required: eligible || requiresHumanReview,
  requires_human_review:requiresHumanReview, action_executed:false } };

Test order_value=120, delay_days=8. Expected proposal: USD 12, approval required, action not executed. Publish.

Module 4

Multi-Agent Support Resolution System

A deterministic orchestrator fans one complex case to specialist agents, joins their evidence, asks a resolution agent to propose an outcome, and sends it to a reviewer.

SpecializationParallel branchesShared case stateCritic/reviewerHuman gate

Scenario

“My laptop arrived damaged, the extended warranty is missing, and I was charged twice. I want a replacement and a refund of the duplicate charge.” This case spans order, product/policy and payment domains.

Case intake→Prepare case→Order specialistPolicy specialistPayment specialist→Merge evidence→Resolution→Reviewer

Why this is controlled multi-agent architecture

  • n8n owns fan-out, fan-in and the approval boundary.
  • Each specialist has a narrow prompt and limited tools.
  • A shared case object carries evidence with provenance.
  • The reviewer cannot execute actions; it can approve, reject, or request revision.
  • The final state is a proposal for human approval.
Design lesson: not every participant needs to be an autonomous agent. Deterministic orchestration around specialized agents is easier to inspect, evaluate and govern.

Before building: duplicate or create new?

Create four new workflows: three reusable specialist sub-workflows and one form-based orchestrator. Reuse the credentials, Qdrant collection, embeddings model and Module 3 operational workflows; do not duplicate the complete Module 3 agent. Build and publish the specialists before configuring the orchestrator.

4C — Build the Payment Specialist workflow

1

Create the workflow input

Create M4C — Payment Specialist. Add trigger Receive Shared Case with required String case_json. Add Code node Inspect Payment Ledger.

2

Add a safe synthetic ledger

Paste this deterministic code. It investigates charges but cannot refund them:

const raw = $json.case_json;
let c; try { c = JSON.parse(raw); } catch { c = { issue:raw }; }
const orderId = c.order_id || (String(c.issue||'').match(/ORD-\d+/i)||[])[0];
const ledger = {
  'ORD-1048': [
    { transaction_id:'CHG-801', type:'charge', amount:120, currency:'USD', status:'settled' },
    { transaction_id:'CHG-802', type:'charge', amount:120, currency:'USD', status:'settled' }
  ],
  'ORD-2055': [
    { transaction_id:'CHG-901', type:'charge', amount:75, currency:'USD', status:'settled' }
  ]
};
const transactions = ledger[orderId] || [];
const settled = transactions.filter(x => x.type==='charge' && x.status==='settled');
const duplicate = settled.length > 1 && new Set(settled.map(x => x.amount)).size === 1;
return { json:{ specialist:'payment', case_json:raw, order_id:orderId || null,
  transactions, duplicate_charge_suspected:duplicate,
  suspected_duplicate_amount:duplicate ? settled[0].amount : 0,
  confidence:transactions.length ? (duplicate ? 'high':'medium') : 'low',
  action_executed:false,
  missing_evidence:transactions.length ? [] : ['No payment ledger found'] } };

{"customer_name":"Asha Rao","order_id":"ORD-1048","issue":"I was charged twice"}

Build one evidence bundle

Add Code node Aggregate Specialist Evidence, Mode Run Once for All Items:

const rows = $input.all().map(i => i.json);
const byName = Object.fromEntries(rows.map(r => [r.specialist, r.result ?? r]));
const rawCase = rows.find(r => r.case_json)?.case_json || '{}';
let sharedCase; try { sharedCase = JSON.parse(rawCase); } catch { sharedCase = { raw:rawCase }; }
return [{ json:{
  case:sharedCase,
  specialists:{ order:byName.order||null, policy:byName.policy||null, payment:byName.payment||null },
  evidence_complete:Boolean(byName.order && byName.policy && byName.payment)
} }];

8

Parse the reviewer JSON safely

Add Code node Parse Reviewer Decision:

const raw = String($json.text ?? $json.output ?? '');
const cleaned = raw.replace(/```json|```/gi,'').trim();
let review;
try { review = JSON.parse(cleaned); }
catch { review = { decision:'ESCALATE', issues:['Reviewer returned invalid JSON'],
  corrected_customer_response:raw, approval_required:true }; }
const allowed = ['APPROVE','REVISE','ESCALATE'];
review.decision = allowed.includes(review.decision) ? review.decision : 'ESCALATE';
return { json:review };
