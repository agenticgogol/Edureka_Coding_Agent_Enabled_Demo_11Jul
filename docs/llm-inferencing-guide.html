BEFORE YOU START

Setup, Glossary & Common Pitfalls

Read this once before Track A. It covers the prerequisites, environment setup, and jargon the tracks assume you already have — plus the mistakes that trip up almost every newcomer.

PREREQUISITES — DO YOU NEED THIS FIRST?
Linear algebra — vectors, matrices, matrix multiplication. Needed to follow attention math (Track C); not needed for Track A.
Probability basics — what a distribution is, what softmax does. Needed everywhere; Track A's sampling section is the easiest place to build this.
Python fluency — comfortable reading/writing scripts, using pip/venv. Assumed throughout.
Gradient descent intuition — "adjust weights to reduce a loss number." Needed for Tracks B and C; not for Track A.
Don't have the math yet? You don't need a full course first. Track A needs almost none of it — start there, and pick up probability and linear-algebra concepts in context as Tracks B and C need them, rather than front-loading a semester of math.
HARDWARE & ENVIRONMENT
  1. Check what you actually have — run nvidia-smi; no output means no usable local GPU. — this decides your entire hardware path below.
  2. Match your CUDA version to your PyTorch build before installing anything else. — a torch/CUDA mismatch is the single most common "it just doesn't work" cause for newcomers.
  3. No local GPU? Use a free or cheap cloud tier — see the table below. — a missing GPU should change where you start, never be a reason to stop.
  4. Check disk space before downloading models — even small open models run 2–15GB each. — running out of disk mid-download is a common, confusing first failure.

GLOSSARY — 20 TERMS USED THROUGHOUT
Parameter / weight — a learned number inside the model; "7B model" means 7 billion of these.
Token — the model's unit of text, roughly a word-piece, not a whole word.
Embedding — a token turned into a vector of numbers the model can compute with.
Logits — the model's raw, unnormalized scores for "what token comes next," before softmax.
Softmax — turns logits into a proper probability distribution that sums to 1.
Loss — a single number measuring how wrong predictions were; training exists to shrink it.
Gradient — the direction/amount to nudge each weight to reduce the loss.
Epoch — one full pass through the training dataset.
Batch size — how many examples are processed together before one weight update.
Checkpoint — a saved snapshot of model weights at a point in training.
Context window — the max number of tokens the model can attend to at once.
Attention — the mechanism letting each token weigh the relevance of every other token.
Inference — running a trained model to produce output, as opposed to training it.
Pretraining — the initial, large-scale pass that builds general language ability.
Fine-tuning — further, smaller-scale training that specializes a pretrained model.
Quantization — storing weights in fewer bits to save memory, at some precision cost.
VRAM — GPU memory; usually the hard limit on model size you can run or train.
Latency / throughput — time to one response vs responses handled per unit time — often a tradeoff.
Base model — a pretrained model before any instruction/chat fine-tuning.
Instruct / chat model — a base model fine-tuned to follow instructions conversationally.
PITFALLS THAT CATCH ALMOST EVERY NEWCOMER
!Not tracking experiments. Even a plain spreadsheet or a free Weights & Biases account — by run 5 you won't remember which config produced which result.
!Trusting vibes over numbers. "This output looks better" is not evaluation — every track's guide ends in a measured comparison for a reason.
!Chat template mismatches. Training or prompting with the wrong template for a given model is the single most common source of "this model is broken" reports.
!CUDA out-of-memory panic. Before assuming you need a bigger GPU: reduce batch size, enable gradient accumulation and gradient checkpointing, or drop to a smaller quantization.
!Ignoring model licenses. "Open weights" doesn't always mean unrestricted commercial use — check before building on top of a specific model.
!Skipping the smoke test. Launching a full run without a 50-step sanity check first turns a 2-minute bug into a 4-hour wasted run.
!No fixed random seed. Without one, you can't tell if a result changed because of your edit or just run-to-run noise.
!Jumping straight to Track C. Pretraining is the least forgiving place to learn debugging — Tracks A and B teach you to read errors on a much shorter feedback loop first.

Four ways to get an LLM working for you — from running something that already exists to building your own from raw data. Same underlying skill stack, wildly different time and cost.

01 Environment & Model Ecosystem ▸

STEPS FROM ZERO

  1. Install Python 3.10+, make a venv, install transformers/torch/huggingface_hub. — this is the toolbox everything else sits on.
  2. Create a Hugging Face account, generate a token, log in via the CLI. — most repos require this even when the model is public.
  3. Install Ollama separately. — gives you a second, simpler path to compare against Transformers.
  4. Pick two small open instruct models (1–3B) and read their model cards in full. — license terms and prompt format differ, and silently break results if ignored.
  5. Pull one via ollama pull, download the other via snapshot_download. — you now have the same "install once" step done two ways.

02 Tokenization & Generation Internals ▸

STEPS FROM ZERO

  1. Load a tokenizer alone and encode/decode a sentence; print the token ids. — makes tokenization concrete instead of abstract.
  2. Compare BPE output across two tokenizers on the same sentence. — shows vocab differences directly affect token count and cost.
  3. Call .generate() with output_scores=True and inspect the first token's logits. — demystifies "next-token prediction" as an actual probability distribution.
  4. Print past_key_values tensor shapes across two decoding steps. — makes the KV cache concrete rather than a term you've only read.
  5. Implement greedy decoding yourself in a 10-line loop, no .generate(). — forces you to see what the convenience function hides.

# (d) loop: argmax logits, append id, feed only the new id back with past_key_values
03 Decoding Strategies & Sampling ▸

STEPS FROM ZERO

CONCEPTS & THEORY
Autoregressive language modeling
The model predicts one next token at a time given everything before it — this single, simple objective is what produces the broad capability you see.
Embeddings & vector space
Tokens become vectors of numbers; tokens with similar meaning end up near each other in that space.
Attention, intuitively
Each token "looks at" every other token with a learned weight, deciding what's relevant to predicting what comes next.
Softmax & probability
Raw model scores (logits) get converted into a proper probability distribution over the vocabulary before a token is sampled.
Why long context is expensive
Standard attention cost grows roughly quadratically with sequence length — the direct reason context windows aren't unlimited and the KV cache matters so much.
Quantization theory
Fewer bits per weight means less memory and faster math, at a precision cost — and not every layer is equally sensitive to that cost.
DEEP DIVE — OLLAMA vs HF TRANSFORMERS, AND WHERE LLAMA.CPP / VLLM FIT

These four aren't competing choices — they sit at different layers of the same stack. Ollama and Transformers are two ways to load and run a model; llama.cpp and vLLM are the engines underneath that actually execute the math. Here's exactly how each differs, procedurally.

PROCEDURE — RUNNING A MODEL VIA OLLAMA
  1. Install Ollama — one binary; it runs a background server.
  2. ollama pull <model> — downloads a pre-quantized GGUF file.
  3. ollama run <model> — Ollama loads the GGUF into llama.cpp under the hood and opens a chat prompt.
  4. Every prompt is tokenized, run through llama.cpp, and streamed back — all inside the Ollama process, invisible to you.
  5. Optionally query the same model over localhost:11434 as a REST API — no extra setup.
PROCEDURE — RUNNING A MODEL VIA TRANSFORMERS
  1. pip install transformers torch — a Python library, not an app.
  2. AutoTokenizer.from_pretrained(model_id) — load the tokenizer explicitly.
  3. AutoModelForCausalLM.from_pretrained(model_id) — load the full-precision weights into memory yourself.
  4. Call tokenizer.encode(), then model.generate() (or write your own loop) — every intermediate tensor is one line of code away from being printed and inspected.
  5. No server, no API — that's a separate step you build (FastAPI, vLLM) if you want one.
HOW LLAMA.CPP WORKS, AND WHEN TO USE IT DIRECTLY
What it is: a C++ inference engine that runs quantized (GGUF) models efficiently on CPU and GPU, with no Python dependency at all. Ollama, LM Studio, and GPT4All are all thin wrappers around it — when you run a model in Ollama, llama.cpp is the code actually doing the matrix math underneath.
  1. How it works: it loads a GGUF file (weights pre-quantized to 4/5/8-bit), builds a compute graph for the transformer, and executes it with hand-optimized CPU kernels (plus optional GPU offload for some layers) — no PyTorch, no Python runtime overhead.
  2. When to use it directly instead of Ollama: when you need a setting Ollama doesn't expose (a specific context length, a custom CPU/GPU layer split, grammar-constrained output), or you're deploying to a device where even Ollama's overhead is unwelcome (embedded, mobile, edge).
  3. How to use it: clone and build the repo, then run its built-in server binary directly — ./llama-server -m model.gguf -c 4096 -ngl 20 starts an OpenAI-compatible API with full control over context size (-c) and how many layers offload to GPU (-ngl).
HOW VLLM WORKS, AND WHEN TO USE IT
What it is: a production-grade inference engine for serving full-precision (or quantized) Transformers-format models with high throughput — the step up from "a model that runs" to "a model that serves many requests at once, fast."
  1. How it works — PagedAttention: manages the KV cache in fixed-size, non-contiguous memory "pages" instead of one big pre-allocated block per request, the way an OS manages virtual memory — this eliminates the memory fragmentation that would otherwise waste a large fraction of GPU memory.
  2. How it works — continuous batching: instead of waiting for a whole batch of requests to finish before starting the next batch, vLLM slots new requests into a running batch the moment a GPU "seat" frees up — a large part of why its throughput beats a naive serving loop.
  3. When to use it: the moment you have more than one concurrent user, or you're benchmarking real latency/throughput rather than just "does it work" — a hand-rolled FastAPI + .generate() endpoint falls over fast under load; vLLM is built for exactly this.
  4. How to use it: pip install vllm, then vllm serve <model_id> — starts an OpenAI-compatible API server, handling batching and the KV cache for you automatically.
When should you use this track? Whenever you need an existing capability without customization — prototyping, personal tools, or deciding whether an open model is good enough for a task at all. If prompting and retrieval genuinely solve your problem, stop here; you don't need Track B or C.
INTERVIEW QUESTIONS
01What does the KV cache save you from redoing on every generated token?
Good answers explain that without it, each new token would require re-running attention over the entire sequence from scratch.
02Why does raising temperature increase diversity but risk coherence?
Flattening the probability distribution makes lower-probability, less "safe" tokens more likely to get picked.
03What's the practical difference between top-k and top-p sampling?
top-k fixes the candidate pool size; top-p adapts pool size to the shape of the distribution at each step.
04What does quantization trade away, and why do 4-bit models often still work well?
Numeric precision, not capability — most weights carry redundancy that lower precision doesn't meaningfully disturb.
05Why can identical model weights produce worse outputs with the wrong chat template?
The model was trained to expect a specific token structure; deviating from it puts it outside its training distribution.
06What's the time complexity of self-attention with respect to sequence length, and why does it matter?
Roughly O(n²) — directly explains why long-context serving is expensive and why techniques like PD disaggregation exist upstream.
07How would you decide between a hand-rolled FastAPI endpoint and vLLM for serving?
Concurrency and throughput requirements — a single-user prototype doesn't need continuous batching; real traffic does.
08What's the difference between latency and throughput, and why can optimizing one hurt the other?
Batching improves throughput but can increase individual request latency — the classic serving tradeoff.
What to expect Claude Code to do — and what it can't fully solve alone: it will create a venv, write and run Python scripts, and download real model weights (a few GB total). Two things it hits that need you: Ollama isn't pre-installed — it'll ask you to run brew install ollama (or your OS equivalent) and start ollama serve yourself, since that's an interactive step. And vLLM has no macOS build (Linux + CUDA/ROCm/TPU only) — on a Mac or any machine without an Nvidia/AMD GPU, expect it to write real vLLM code but tell you it can't execute that one piece locally, and suggest Colab or a rented GPU box instead of faking a result.

Fine-Tuning

Adaptation fluency: take a base or instruct model and specialize it — SFT, LoRA/QLoRA, and preference tuning, evaluated rather than assumed.

01 Deciding to Fine-Tune & Curating Data ▸

STEPS FROM ZERO

  1. Write down the exact task the base model fails at with best prompting. — fine-tuning without a documented gap is fine-tuning blind.
  2. Try RAG or better prompting first on 10 real examples. — many "fine-tuning" needs are actually retrieval/prompting gaps, cheaper to fix.
  3. Hand-write 50–100 examples in the target format before generating more. — surfaces format/edge-case problems synthetic generation hides.
  4. Deduplicate and check for leakage into your eval set. — contamination silently inflates your later "it worked!" result.
  5. Scale to 500–1000 examples: hand-written + reviewed synthetic. — reviewed small data beats large unreviewed data for SFT.

RELATED CONCEPTS

RAG vs fine-tuninginstruction formatsynthetic datatrain/eval contamination

PROS / CONS

PROS
  • Forces clarity on the real problem before spending GPU time
CONS
  • Genuinely tedious — tempting to skip straight to training

WHEN TO USE

Every fine-tuning project, no exceptions — this is the step people skip and later regret.

02 SFT Mechanics & Tooling ▸

STEPS FROM ZERO

  1. Install transformers, trl, peft, bitsandbytes, accelerate. — the standard stack you'll reuse for every method after this.
  2. Apply the exact chat template you intend to use at inference. — a train/inference template mismatch quietly ruins results.
  3. Mask loss on the prompt tokens, train only on completions. — without this the model partly "learns" to predict your own instructions.
  4. Turn on sequence packing for short examples. — big throughput gain, negligible downside.
  5. Run a tiny 50-step smoke test before a full run. — catches broken configs before burning hours of GPU time.

RELATED CONCEPTS

loss maskingsequence packingSFTTrainergradient checkpointingmixed precision

PROS / CONS

PROS
  • Standard, well-documented, works full or partial
CONS
  • Full fine-tuning needs meaningfully more VRAM than PEFT

WHEN TO USE

SFT is the baseline for any adaptation task — do it before LoRA/QLoRA so you have the full-fine-tune reference point.

03 Parameter-Efficient Fine-Tuning (LoRA / QLoRA) ▸

STEPS FROM ZERO

  1. Repeat your SFT run with a LoRA adapter instead of full weights. — directly compare full fine-tune vs LoRA on the same data/model.
  2. Try rank=8 and rank=32 on the same task. — builds intuition for the rank/capacity tradeoff instead of guessing.
  3. Load the base model in 4-bit and repeat as QLoRA. — shows how much VRAM QLoRA actually saves vs fp16 LoRA.
  4. Merge the adapter back into base weights; compare inference speed. — merged models serve like normal models; unmerged need adapter-aware serving.
  5. Try Unsloth on the same task and compare training speed. — shows the gap between "correct" and "fast" implementations.

RELATED CONCEPTS

low-rank decompositionLoRA rank/alphaNF4 quantizationadapter mergingUnsloth / Axolotl

PROS / CONS

PROS
  • Trains on a single consumer GPU, fast iteration
CONS
  • Slightly lower ceiling than full fine-tuning on large distribution shifts

WHEN TO USE

The default choice for almost all practical fine-tuning — reach for full fine-tuning only once LoRA demonstrably underperforms.

04 Preference Tuning & Alignment ▸

STEPS FROM ZERO

  1. Generate 2 responses per prompt on 50–100 prompts from your SFT model. — you need response pairs to express a preference between.
  2. Label which response is better (yourself or LLM-as-judge). — this is the signal DPO trains on; its quality gates everything downstream.
  3. Run DPO on top of the SFT model using the preference pairs. — the practical, most-used alignment method, far cheaper than full RLHF.
  4. Compare DPO vs SFT-only outputs on held-out prompts. — alignment should show up as measurable, not just felt.
  5. Read how RLHF's reward-model + PPO loop works, without implementing it. — gives you the vocabulary to reason about it even if you never run PPO yourself.

RELATED CONCEPTS

preference datasetsDPORLHF (reward model + PPO)KTO / ORPO

PROS / CONS

PROS
  • Simple to run, meaningfully shapes tone/behavior
CONS
  • Bad preference data causes reward-hacking-like behavior

WHEN TO USE

Once SFT alone isn't giving you the right behavior/tone — not a required step for every fine-tune.

05 Evaluating & Serving a Fine-Tune ▸

STEPS FROM ZERO

  1. Build a held-out eval set (30–50 examples) untouched by training. — without this you can't honestly claim the fine-tune worked.
  2. Score base vs SFT vs DPO on the same eval set. — isolates exactly what each stage contributed.
  3. Test 5–10 prompts unrelated to your task. — catches catastrophic forgetting: quiet general-capability loss.
  4. Serve via a multi-adapter-aware server (vLLM supports LoRA directly) instead of merging. — lets you host several fine-tunes off one base efficiently.

RELATED CONCEPTS

held-out evalLLM-as-judgecatastrophic forgettingmulti-LoRA serving

PROS / CONS

PROS
  • Closes the loop from "I fine-tuned something" to proof it's better
CONS
  • Building a good eval set is as much work as the fine-tune itself

WHEN TO USE

Non-negotiable last step of every fine-tuning project — an unevaluated fine-tune is an unfinished one.

CONCEPTS & THEORY
Transfer learning
Starting from a pretrained model is dramatically cheaper than training from scratch because it already encodes general language and world knowledge.
Loss masking
Predicting the prompt itself isn't the objective — only completion tokens should contribute to the training signal.
Low-rank adaptation, intuitively
A large weight update can often be well-approximated by the product of two much smaller matrices — that approximation is the entire idea behind LoRA.
Preference optimization
DPO reframes "align to human preference" as a classification-like objective over response pairs, without a separate reward model or an RL loop.
Catastrophic forgetting
Gradient updates on a narrow dataset can overwrite general capabilities that weren't reinforced during fine-tuning.
Overfitting on small data
A narrow, small fine-tuning set risks the model memorizing examples rather than generalizing the underlying behavior.
When should you use this track? When prompting and retrieval genuinely can't get the exact behavior, tone, or output-format reliability you need, and you have — or can build — a few hundred quality-labeled examples. Skip it if the need is pure knowledge lookup (that's RAG territory) or you don't have enough examples to avoid overfitting.
INTERVIEW QUESTIONS
01When would you choose LoRA over full fine-tuning, and vice versa?
LoRA for most practical adaptation on limited hardware; full fine-tuning when the task needs a bigger distribution shift than low-rank updates can capture.
02What does "rank" control in a LoRA adapter?
The capacity/expressiveness of the low-rank update — higher rank approaches full fine-tuning capacity at higher cost.
03Why does QLoRA quantize the base model but keep the adapter in higher precision?
The frozen base just needs to be read cheaply; the adapter is what's actually being trained and needs precision for stable gradients.
04What problem does DPO solve that plain SFT doesn't?
SFT teaches "produce this output"; DPO teaches "prefer this output over that one," a better fit for tone/style/safety shaping.
05How would you detect catastrophic forgetting in a fine-tuned model?
Probe with prompts unrelated to the fine-tuning task and compare against the pre-fine-tune baseline.
06Why is a held-out eval set non-negotiable?
Without one, you can't distinguish genuine improvement from memorization of the training data itself.
07What's the risk of using an LLM-as-judge for evaluation?
Judge models carry their own biases and blind spots — mitigate with rubric-based prompts and periodic human spot-checks.
08How would you serve five different LoRA fine-tunes of the same base model efficiently?
Keep adapters unmerged and use a multi-adapter-aware server like vLLM instead of hosting five separate merged models.

01 Data Pipeline & Tokenizer ▸

STEPS FROM ZERO

  1. Download a small (1–10GB) slice of an open pretraining dataset (e.g. FineWeb-Edu). — full-scale crawl data is unnecessary and unmanageable for an SLM learning project.
  2. Run a basic quality filter and measure how much data it removes. — shows firsthand how much raw web data is actually junk.
  3. Run MinHash deduplication on your slice. — duplicate data wastes compute and can cause memorization artifacts.
  4. Train a BPE tokenizer from scratch at two vocab sizes. — makes the vocab-size tradeoff (sequence length vs embedding table size) concrete.
  5. Tokenize and pack the dataset into fixed-length sequences. — this is the actual input format your training loop consumes.

02 Architecture Design ▸

STEPS FROM ZERO

  1. Implement a minimal decoder-only block (attention + MLP + residuals), no tricks. — forces you to understand the base architecture before adding complexity.
  2. Add RoPE and verify generation still works. — standard in every modern open model; understand it by implementing it once.
  3. Swap LayerNorm→RMSNorm and add SwiGLU; compare training stability. — these specific changes separate GPT-2-era models from modern ones.
  4. Implement grouped-query attention; calculate KV-cache memory savings. — makes the inference-time payoff tangible, not just theoretical.
  5. Pick a target param count and work backward to depth/width. — prevents architecture choices that are needlessly hard to train or serve later.

03 Pretraining Loop & Mechanics ▸

STEPS FROM ZERO

  1. Start from nanoGPT or litGPT rather than writing the loop fully from scratch. — read-then-write: the scaffold encodes solved problems you don't need to re-solve.
  2. Swap in your own architecture and confirm it trains on a toy dataset. — isolates architecture bugs from training-loop bugs.
  3. Set AdamW + cosine LR schedule + warmup; log loss every N steps. — this specific recipe is what makes transformer pretraining stable in practice.
  4. Deliberately induce a loss spike and practice recovering from checkpoint. — loss spikes happen in real runs; build the recovery muscle memory before it costs you one.
  5. Run the full training job on your prepared dataset, checkpointing regularly. — everything before this was rehearsal; this is the actual pretraining run.

CONCEPTS & THEORY
Chinchilla scaling laws
For a fixed compute budget there's an optimal balance of model size vs training tokens — oversized models trained on too little data waste compute.
Why data quality dominates at small scale
An SLM has far less capacity to "average out" noisy or duplicate data than a frontier-scale model does.
The positional encoding problem
Transformers have no inherent sense of token order; RoPE injects relative position information directly into the attention computation.
Pre-norm vs post-norm
Modern models place normalization before each sub-layer rather than after — what makes very deep transformers trainable at all.
Why AdamW, not plain SGD
Adaptive per-parameter learning rates handle the wildly different gradient scales across a transformer's layers far better than a single fixed rate.
Compute-cost estimation
A rough FLOPs-per-token formula (~6N per token, N = parameter count) lets you estimate training time and cost before committing to a run.
When should you use this track? Only when your actual goal is to understand or need the pretraining process itself, or no usable open base model exists for your domain or language. For almost every applied product need, an existing base model plus Track B is faster, cheaper, and better — treat Track C as a learning/foundational track, not a shortcut to a better product model.
INTERVIEW QUESTIONS
01What does the Chinchilla scaling law say, and why did earlier models like GPT-3 violate it?
Compute-optimal training balances model size and token count; GPT-3-era models were oversized relative to the data they were trained on.
02Why is a cosine LR schedule with warmup preferred over a constant learning rate?
Warmup avoids early instability from large updates on randomly initialized weights; decay lets the model settle into a minimum later in training.
03What typically causes a loss spike during pretraining, and how do you recover?
Often a bad data batch or momentum buildup; recover by rolling back to a recent checkpoint and adjusting LR or gradient clipping.
04What does grouped-query attention save relative to standard multi-head attention?
It shares key/value projections across groups of query heads, cutting KV-cache memory substantially with minimal quality loss.
05Why does deduplication matter more than most newcomers expect?
Duplicate data wastes training compute and can cause the model to memorize rather than generalize from that content.
06Mechanically, what's the difference between a base model and an instruct model?
A base model is purely next-token-trained on raw text; an instruct model has additional SFT (and often preference tuning) on top.
07How would you decide your model's vocabulary size?
Balance sequence length (smaller vocab → longer sequences) against embedding table size (larger vocab → more parameters in embeddings alone).
08Why might your 150M-parameter model underperform a 1B-parameter open model even with clean data and a solid architecture?
Parameter count itself is a capacity ceiling — good data and architecture get you to that ceiling efficiently, they don't raise it.
