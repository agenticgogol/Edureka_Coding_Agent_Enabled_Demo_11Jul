Skill internals · teaching track

From System Design to a Running Demo

Three skills, one relay: teaching-brief-from-system-design drafts the brief, teaching-brief gets it actually approved, and teaching-build turns the approved brief into real code. This page explains what each one is, why it exists, and exactly what it does step by step.

Human approval required Skill / subagent call Claude reasoning (no tool) File written to disk
01

teaching-brief-from-system-design — the bridge

The teaching track and the architecture-design track were built independently — one doesn't know the other exists. This skill's whole job is translation: take an already approved architecture design and pre-fill the teaching brief's fields from it, so nothing gets asked twice.

What it actually does

It reads the approved architecture_design.md (or the eight system_design/ stage files) plus the raw usecase description and requirements answers already gathered upstream, then maps specific sections of the architecture doc onto specific fields of teaching_brief.md — nothing is re-derived from scratch, and nothing is invented if the mapping is genuinely ambiguous (in that case the field is left blank for teaching-brief to ask fresh, never guessed).

Input
Approved architecture_design.md / system_design/, plus the usecase description and requirements-checklist answers (problem/user, input, output, tools, frontend, backend, memory, provider, non-goals)
Output
A draft teaching/<slug>/teaching_brief.md — every checkpoint it fills is marked pending, never approved

02

teaching-brief — what it really is

The teaching brief is the contract everything downstream builds against — one living Markdown file, teaching/<slug>/teaching_brief.md, that records every decision plus whether a human actually approved it. Nothing in teaching-build runs until every checkpoint in this file reads approved, not just pending.

Nine checkpoints, each a real stop

Project description

Freeform, from the user. If a brief already exists, resume from the first unapproved checkpoint instead of re-asking.

Parse & clarify gaps

Silently split into "already answered" (restate for confirmation) vs. "genuinely open" (ask, with a recommended default).

Format

Notebook/progressive script, or full Streamlit + FastAPI app. This single answer decides which half of teaching-build runs later.

Happy-path test case

One end-user scenario in plain language — what they'd click, what they'd see. Requires explicit approval or correction.

.env / API key

User confirms the key is set, but require-api-key still runs a real verification call regardless — a "yes" is not itself proof.

Observability

Phoenix tracing wired in, or skipped for this demo.

Vector store & RAG mode

ChromaDB / FAISS / Qdrant Cloud / none — and if a store is chosen, whether retrieval is a single fixed step or an agentic loop that decides/grades/retries.

External tools (MCP-first)

For any needed capability, a live lookup checks for a free public MCP server before ever assuming custom tool code — and recommends it by default when found.

Ready to generate?

Everything is summarized in one block. Only an explicit "yes" here releases control to teaching-build.

The brief file's shape

Every field below lives in teaching/<slug>/teaching_brief.md, and the ## Checkpoint status block is the actual gate — teaching-build reads this file, not the conversation history, to know what it's allowed to do.

## Description
## Steps (a, b, c… each building on the last)
## Format notebook | full_app
## Happy-path test case (user-approved)
## Observability phoenix | none
## Vector store chromadb | faiss | qdrant | none
## RAG mode fixed | agentic | n/a
## Agentic RAG capabilities core + confirmed optional set
## MCP tools server name(s), or none/declined
## Constraints required env vars
## Audience level
## Decisions "your call" answers, never re-asked
## Checkpoint status
  - Format: approved | pending
  - Ready to generate: approved | pending
  - Build: complete | pending
03

teaching-build — how the code actually gets written

This is the one skill that turns an approved brief into runnable files. It reads ## Format first and follows one of two entirely different procedures.

Step 0 — read the Format field, branch immediately

notebook and full_app are not two flavors of the same steps — they're genuinely different builds, and this skill refuses to build a notebook when the brief says full_app, or vice versa.

Path A — notebook / small script

Creates teaching/<slug>/notebook.ipynb. For every step in the brief's ## Steps list, in order:

Cell 1
Markdown — what this step adds and why, 2–4 sentences
Cell 2
Code — previous step's code plus this step's addition, clearly delineated, runnable on its own once prior cells have run
Cell 3
Output showing it actually working — a printed response, tool-call trace, or retrieved chunks
skill

helper-utils — reused across every step once the sequence is non-trivial (e.g. a 5-step demo), so step (a)'s client setup carries forward.

skill

agent-mcp-real (Mode B) — if ## MCP tools names a server, the tool-calling step connects to that real server process rather than a hand-written function.

skill

synthetic-data-generator — only if invoked standalone and data/ is missing something a step needs; normally the calling pipeline already ran this before teaching-build starts.

skill

agent-agentic-rag — only if ## RAG mode is agentic; builds the decide/retrieve/grade/rewrite loop instead of one fixed retrieval call, and shows each round printed live.

boundary

No mock mode, ever — every step calls the real provider that require-api-key already verified before this skill started.

Path B — full_app (Streamlit + FastAPI)

A lighter version of the full projects/ build chain — real code, real provider calls, still no mock mode, but it skips the shippable-project ceremony (lint-and-typecheck, validate-env, a formal plan.md).

Step 0 of this path — inline or delegated? Always asked, never assumed

Complexity is evaluated from what's actually in scope for this build call — step count, whether a vector store or observability is wired, existing code size if appending. Claude states its recommendation and reasoning, then waits for the user to choose.

Inline

Low complexity — 1–2 steps, no vector store, no observability. Claude builds it directly in this conversation, steps 1–7 below.

Delegated

Higher complexity — 3+ steps, or store + observability both wired. backend-builder and frontend-builder run as separate subagents against the brief (standing in for design.md), then integrator reconciles them.

2vector-storeonly if Vector store ≠ none

If ## RAG mode is agentic, step 2 also runs agent-agentic-rag on top of the vector store, wiring only the capabilities the brief actually confirmed — and subagent summaries are treated as intent, not fact, so the manual contract check in step 6 still happens even after delegated builders report back.

The whole relay, in one paragraph

  1. teaching-brief-from-system-design reads an already-approved architecture design and drafts teaching_brief.md — every field pending, nothing assumed approved.
  2. teaching-brief walks through nine checkpoints for real, mostly confirming the draft rather than asking cold — but format, happy-path, API key, observability, vector store, and "ready to generate" all need a genuine yes.
  3. teaching-build reads ## Format, branches into notebook or full_app, and — for full_app — asks whether to build inline or delegate to subagents before writing a single line of code.
  4. Only after that does teaching-verify (outside this page's scope) drive the result end to end against the real provider.

Command internals · eval track

How an Agent Gets Evaluated /eval-run-pipeline-new [project-folder] [fast-forward] [through-cost-optimize]

This command doesn't run its own evaluation logic — it's a continuity layer over nine phases, each owned by its own skill, each with its own review or cost-approval pause that this command is explicitly forbidden from skipping. The point of the command is to never make you re-type the next slash command; the point of the phases is grounded-theory rigor — nothing gets measured until a human has actually looked at real traces first.

Human pause / approval Skill call Real-API cost approval File / artifact produced

Step 0 — resolve the folder. The first token in the arguments (unless it's fast-forward/through-cost-optimize) names the project being evaluated, e.g. teaching/incident-root-cause-agent. If none is given, the command asks — it never guesses from the current directory.

Step 1 — check where this project already is. Before running anything, it invokes eval-loop to read the pipeline's state file and cross-check it against the real files on disk. A re-run of this command on the same project resumes from the first incomplete phase — it never restarts from phase 0 on a project with existing progress.

Three rules that hold across every phase

These aren't phase-specific — they're enforced by this repo's CLAUDE.md and apply to every skill in the eval suite, not just the ones that mention them locally.

No metrics before error analysis

A judge or metric can't exist for a failure mode that wasn't derived from real open/axial coding (phases 2–3). An invented category measures nothing real.

No statistics computed by the model

Kappa, TPR/TNR, bias correction, bootstrap CIs, stratified splitting all live in exactly one place — evallib/stats.py. No skill re-derives the formula inline.

No held-out reads during iteration

The locked held-out split is read exactly once per calibration cycle, at explicit user confirmation, with a dedicated environment flag set for that call — enforced mechanically by a hook, not just instruction.

What "fast-forward" actually changes

Without it, every pause above stops and waits — exactly as if you'd run each skill by hand.

With it, Claude may proceed through judgment-call pauses using a skill's own stated default (e.g. hint-mode off, primary annotator = first labeler) — and must log every such assumption plainly in the final report.

Never skipped, fast-forward or not: real-money cost approvals, and the explicit "yes" before reading the locked held-out split. Those always require the user.

Any stage failing: stop, report the real error output (not a summary), fix it, and re-run that stage and any stage whose output it invalidates — a fix during integration means re-running the test gate and verify too, not just continuing forward. Later bug reports (after Stage 12 already passed once) go through /fix-bug <kind> <slug> <description> instead of a full re-run of this pipeline.

Command internals · post-ship fix

Fixing a Reported Bug /fix-bug <projects|concepts|teaching> <slug> <bug description>

The short command in this repo — four stages, no design work, no rebuild from scratch. It exists specifically for the case where run-and-verify (or teaching-verify) already passed once, and something broke after that. It is not for a first build — that's what /run-pipeline or /run-teaching-pipeline are for.

Human input required Skill call File updated
$ /fix-bug teaching incident-root-cause-agent "the chat UI hangs after the third message"
kind = teaching   slug = incident-root-cause-agent
bug description = everything after the slug, verbatim in the user's own words
1

Confirm the unit was actually built

Checked before anything else runs:

projects / concepts → plan.md must exist.
teaching → teaching_brief.md must exist and have been through teaching-build at least once (real notebook / app.py / backend+frontend files present).

If not: told plainly this unit hasn't been built yet, and stops — there is nothing to debug.

2

Get a real reproduction

A vague report ("it doesn't work," "chat is broken") is not enough to act on.

Claude asks for the minimum needed to reproduce: what the user did, what they expected, what actually happened (exact error text, wrong output, etc.) — it does not start guessing at causes from a vague description.

3

Route to the matching debug skill

Which skill runs depends on kind and, for teaching, the brief's Format:

projects / concepts

project-debug

teaching, Format: notebook

teaching-debug

teaching, Format: full_app

project-debug — already handles frontend/backend contract issues

Whichever runs: reproduce the real failure, diagnose, fix one hypothesis at a time, re-run until the reported behavior actually works — not until it looks plausibly fixed.

4

Re-certify — not just the one symptom

A bug fix isn't done until the whole gate is green again, not just the reported symptom:

projects / concepts → re-run run-tests (full suite), and run-and-verify too if the fix touched anything on the request path.
teaching → re-run teaching-verify (top to bottom for notebook, the full happy-path flow again for full_app).

5

Record what changed

<kind>/<slug>/README.md's "Testing" section gets updated with what was wrong and what changed — the only file this command touches outside the actual fix.

Why this exists separately from the full pipeline

During an initial build, the pipeline's own test/verify stages already call the matching debug skill automatically the moment something fails — you never need this command for that. /fix-bug is only for a failure discovered after a unit already shipped once: it skips straight to reproduce → fix → re-certify, without re-running clarify, design, or the full build chain that produced the working version in the first place.
