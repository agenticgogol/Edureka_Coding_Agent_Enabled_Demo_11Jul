Day 1 · Part 0 · 12 minCORE

The Incident: Why Agents Change the Security Model

Start with consequences, not definitions. Students see an agent turn untrusted language into real authority before learning the vocabulary.

Recognize
why agent security is more than chatbot safety
Separate
model failure from system failure
Anchor
the course on blast radius and recoverability
Theory — mechanism, not slogan

A traditional application usually executes a developer-written control flow. An agent inserts a probabilistic decision-maker into that flow: it interprets instructions, chooses tools, composes parameters, loops, stores state, and may delegate. The key change is not that the model can say something wrong; it is that model output can become authority-bearing input to another system.

Security therefore has two jobs. First, reduce the chance that the model is manipulated or mistaken. Second—and more important—make sure a manipulated model still cannot exceed the authority the application intended to grant. This is why “the model refused the attack” is evidence of model behavior, not proof of system security.

Use one running system, OrderCare: it can search policy, read an order, issue a refund, draft/send email, and remember customer preferences. Every module either corrupts one of those paths or constrains it.

Design invariant: Assume the model can be fully fooled. Ask what the system still prevents.
Probability controlsClassifiers, prompting, provenance and normalization reduce the chance of bad reasoning.
Consequence controlsAuthorization, hard limits, isolation, approvals and circuit breakers cap what bad reasoning can do.
Detection controlsTracing and alerts shorten time-to-detect.
Recovery controlsRevocation, compensation and kill switches shorten time-to-contain.
Deep dive · common mistakes and nuance

Do not open with system-prompt extraction as the scariest outcome. Prompt text is often far less valuable than credentials, tenant data, tool authority, or persistent memory. Teach students to rank outcomes by asset impact, not visual drama.

The course uses OWASP ASI01–ASI10 as a coverage check, not as a substitute for threat modeling.

Threat Modeling: Assets → Trust Boundaries → Invariants

Replace the current three-question shortcut with a procedure students can apply to any agent, while keeping the shortcut as a final sanity check.

Inventory
assets, actors, tools and side effects
Trace
untrusted data and authority across boundaries
Define
security invariants before choosing guardrails
Theory — mechanism, not slogan

A useful agent threat model starts with assets and authority. What can be read, changed, sent, spent, executed, remembered, or delegated? Then identify who can influence each input: end user, retrieved document author, MCP server, peer agent, model provider, tool response, developer, or compromised dependency.

Next draw trust boundaries. A boundary is not merely a network hop. It is any place where the trust level, identity, tenant, privilege, persistence, or side-effect class changes. A retrieved KB chunk crossing into model context is a trust boundary. A model-generated amount crossing into a payments API is another. A sub-agent return entering an orchestrator is another.

Finally write security invariants: statements that must remain true even if the model is wrong. Examples: “A user can never refund an order they do not own”; “No single agent can send more than 20 emails per task”; “Untrusted code cannot access ambient credentials”; “Memory from tenant A can never influence tenant B.” Guardrails are implementation mechanisms for these invariants.

AssetWhat has value or causes harm if disclosed, altered, spent, executed or persisted?
Attacker controlWhich fields, documents, tool outputs or peer messages can an adversary influence?
Authority transitionWhere does data become a privileged action?
InvariantWhat must remain true even under model compromise?
Deep dive · common mistakes and nuance

STRIDE remains useful for classic components, but agentic systems need explicit modeling of goals, context, tool authority, memory and delegation. Use traditional AppSec methods plus these new semantic/authority surfaces.

Keep the original “worst action / reversible / human required?” questions as a fast severity triage after the detailed model, not as the whole threat model.

Defense-in-Depth: Guardrail Types & Placement

Teach students where controls belong and why deterministic enforcement near the side effect is usually stronger than a prompt-level rule.

Classify
preventive, detective, containment and recovery controls
Place
controls at the boundary they actually govern
Prioritize
capability controls for high-blast-radius actions
Theory — mechanism, not slogan

“Guardrail” is an umbrella term. Some guardrails influence model behavior (system instructions, classifiers, provenance), some enforce application policy (authorization, schemas, limits), some contain execution (sandboxes, egress controls), and some detect/recover (traces, alerts, revocation, kill switches). Mixing these categories produces false confidence.

Place controls as close as possible to the thing they protect. A refund limit belongs in the refund policy/tool boundary, not in a paragraph of the system prompt. Tenant isolation belongs in the data layer. Egress restrictions belong in the execution environment. This is the reference monitor idea: the component enforcing policy should be hard to bypass and should see every relevant request.

Defense-in-depth does not mean adding many weak filters. It means independent layers with different failure modes: a poisoned document may beat a classifier, but cannot widen an OAuth scope; a compromised model may generate shell code, but cannot escape a deny-all network sandbox; a human may approve a wrong action, but an amount cap can still block it.

Rule of thumb: The higher the blast radius, the less you should rely on the model to police itself.
Model-facingInstruction hierarchy, content separation, input/output classifiers.
Capability-facingAuthz, parameter validation, limits, rate budgets, idempotency.
Environment-facingSandbox, filesystem, egress, secret isolation.
Operations-facingTracing, alerts, revocation, kill switch, incident playbook.

Knowledge Check 1 · Foundations

Answer before revealing. The question is always: would this actually stop the harmful system outcome?

Question 1

The system prompt says “never refund over $50.” There is no tool-side cap. Is the refund protected?

Reveal answer
No. The model is policing itself. A prompt change, injection or model error can bypass it; the refund service must enforce the invariant.
Question 2

The user is authenticated. Can the agent safely read any order ID the model generates?

Reveal answer
No. Authentication proves who the user is; resource-level authorization must still verify tenant/ownership and allowed action.

An injected document successfully hijacks the model, but the refund tool rejects the forbidden action. Was the whole system compromised?

Reveal answer
The model was compromised; the protected side effect was contained. Track both facts separately. This distinction is central to the course.

Identity, Authorization & Tool Safety

Make the distinction between authentication, authorization, delegation and business-policy validation explicit.

Distinguish
who the caller is vs what they may do
Constrain
scope, resource, amount and time
Validate
tool arguments independently of model intent
Theory — mechanism, not slogan

Authentication answers “who is this actor?” Authorization answers “may this actor perform this action on this resource?” Delegation answers “what subset of that authority may this agent use for this task?” Agent systems often do authentication correctly and then skip the other two by running every tool under one broad service account.

Tool authorization should combine identity policy and business invariants. A user may have refund:write but only for orders they own, only up to a per-transaction amount, only under a daily aggregate budget, and perhaps only while the task token is valid. The model chooses a desired action; the tool boundary decides whether it is allowed.

Parameter schemas are security controls too. Use typed enums, bounded numeric ranges, canonical resource IDs, allowlisted destinations, maximum row counts and explicit side-effect classes. Avoid free-form “command” or “URL” parameters when a narrow structured field can represent the task.

Least functionalityExpose only tools the task actually needs.
Least privilegeGrant only the scopes/resources required.
Least autonomyRequire approval for high-risk or irreversible actions.
Least durationUse short-lived, revocable authority where possible.
Deep dive · common mistakes and nuance

Per-call caps alone are bypassable through structuring. Add aggregate and velocity limits keyed to the right principal: user, account, tenant, task and tool.

Validate at execution time, not only when the model first proposed the action; asynchronous workflows may change state between approval and execution.

Prompt Injection & Agent Goal Hijack

Teach injection as a trust-boundary problem and explicitly avoid implying that tags or a classifier “solve” it.

Explain
direct vs indirect injection and goal hijack
Layer
probability-reduction with consequence-reduction
Design
data/instruction separation plus capability controls
Theory — mechanism, not slogan

Prompt injection occurs when attacker-controlled content changes the model’s behavior in a way the application did not intend. In an agent, the dangerous outcome is often goal hijack: retrieved or user-supplied content diverts the agent from the user’s legitimate goal toward data exfiltration, tool misuse, or persistence.

Direct injection arrives from the conversational user. Indirect injection arrives through content the agent reads: a web page, email, ticket, document, code comment, image transcription, tool result, memory record or peer-agent message. Indirect injection is particularly dangerous because the victim user may be completely benign.

Provenance tags and instruction hierarchy are useful because they make trust distinctions explicit to the model. But they are soft controls: the same model still reads both the attacker text and the rule telling it not to obey. A classifier is also probabilistic and may disagree with the main model after normalization or across multiple turns. Treat both as detection/risk-reduction—not as a hard security boundary.

The stronger architecture minimizes how much untrusted content reaches privileged planning, authorizes retrieval by tenant/task, strips active metadata where appropriate, separates reading from acting, and puts deterministic authorization around every side effect. The question is not “can I make the model never follow an injected instruction?” but “if it does, what can it actually accomplish?”

Source provenanceTrack origin, author, tenant, retrieval reason and trust level.
Context minimizationRetrieve only the smallest task-relevant content.
Instruction/data separationRepresent external content as quoted/untrusted evidence, not policy.
Capability containmentNo injected text may grant scope, change limits or bypass approval.
Deep dive · common mistakes and nuance

System-prompt extraction is not automatically a critical vulnerability. Treat secrets in prompts as a design error; assume prompts may be exposed and keep credentials/authorization outside them.

Do not auto-decode arbitrary base64/hex and feed the decoded result into the main model as a “defense”; decoding can expand the attack surface. Normalize for inspection, preserve provenance, and apply policy to the canonical representation.

Output Handling, Data Leakage & Grounded Actions

Move beyond “PII regex” and teach output as another trust boundary, especially when model output is consumed by code or another agent.

Protect
sensitive data upstream and downstream
Validate
structured outputs before execution/rendering
Ground
claims and actions in authorized evidence
Theory — mechanism, not slogan

Output security has two distinct problems. First, disclosure: the response may contain data the caller should never see. Second, unsafe consumption: a downstream renderer, SQL engine, shell, browser or agent may treat model output as executable content. “The model generated it” does not make it trusted.

The strongest disclosure control is upstream data minimization and row/column authorization: do not put another tenant’s data in context. Output redaction is a second net for residual leakage. For structured outputs, validate against a strict schema and re-check authorization on resource IDs before execution.

Grounding is not simply “ask for citations.” A security-relevant claim should link to authorized evidence, and the application should distinguish factual evidence from the model’s interpretation. For an action, record which evidence and policy led to the proposal so a human or auditor can reconstruct it.

Prevent exposureTenant/RLS/column policy before retrieval.
Sanitize egressPII/secret detection as a backstop.
Safe consumptionEscape/validate output for the destination context.
Evidence bindingAction proposal references source IDs and policy version.
Deep dive · common mistakes and nuance

Insecure output handling can become classic injection: HTML/Markdown, SQL, shell, spreadsheet formulas, URLs and code all have destination-specific escaping/validation rules.

A “grounding score” is not an authorization decision. A well-grounded request can still be forbidden for this caller.

Defense: Never execute free-form model strings directly; use typed operations or a sandbox and validate/escape destination-specific parameters.

Memory & Context Poisoning

Add the missing persistent-state module: a one-turn injection becomes far more dangerous when it survives into future sessions.

Model
memory as a write/read lifecycle
Protect
tenant, provenance, TTL and memory type
Recover
audit, quarantine and delete poisoned state
Theory — mechanism, not slogan

Agent memory changes the time horizon of an attack. A malicious input no longer needs to win the current turn; it can plant a preference, summary, tool hint or “fact” that the agent will trust later. OWASP ASI06 treats this as Memory & Context Poisoning because the damage can persist across sessions and influence future planning or tool use.

Memory needs two gates. The write gate decides what kinds of information may become persistent state, under which tenant/user, with what provenance, confidence and TTL. The read gate decides which memories are relevant and authorized for the current task, and how much trust the model should place in them.

Do not let the model write arbitrary natural-language “instructions for future self” into long-term memory. Prefer typed memory classes: user preference, verified fact, task checkpoint, security decision, etc. Some classes should require evidence or human confirmation. Security policy and credentials should not live in mutable agent memory at all.

Recovery matters: version memory, record who/what wrote it, support deletion/quarantine, and make memory searchable during incident response. A system that cannot answer “which future sessions consumed this poisoned record?” cannot contain a memory incident.

Write-time policySchema, provenance, allowed memory types, tenant binding, TTL.
Read-time policyTask relevance, tenant authz, trust score, source visibility.
Immutable policySecurity rules live outside mutable memory.
ForensicsVersioning, consumers, quarantine, deletion and replay.
Deep dive · common mistakes and nuance

Memory summaries are themselves model outputs and can silently convert an uncertain statement into an authoritative-looking fact. Preserve source references and uncertainty instead of storing only the compressed prose.

Shared vector stores need tenant isolation and deletion semantics; “we filtered in the prompt” is not a data-security boundary.

Observability, Circuit Breakers & Incident Response

Teach telemetry as a security control and show how to contain failures when prevention misses.

Trace
root human → model → tools → side effects
Detect
anomalous loops, privilege use and data movement
Contain
with revocation, drain mode and kill switch
Theory — mechanism, not slogan

A secure agent system must be reconstructable. Every side effect should be traceable to the root user/service identity, task, model decision, evidence, tool parameters (redacted where necessary), policy verdict, credential/capability used, and resulting external ID. “The agent did it” is not an audit trail.

Theory — mechanism, not slogan

Attackers vary representation: Unicode confusables, zero-width characters, HTML/Markdown, images/OCR, code comments, nested quotes, alternate languages and long-context placement. A detector that sees a different canonical representation from the main model can miss content the model still interprets.

Red-team with adaptive attackers that learn from denials and vary sources, not only a static list of jailbreak strings. But keep a frozen regression suite too, so improvements do not accidentally reopen known failures.

Theory — mechanism, not slogan

“Rogue agent” should not be taught as science fiction. Operationally, the concern is a system that acts outside intended control: bypasses policy checks, hides actions, persists unwanted state, modifies its own instructions/tools, creates new agents, acquires resources, or continues acting after the user’s task should have ended.

The architectural response is to keep the security control plane outside the agent’s editable state. The model should not be able to modify its own authorization policy, credential broker, audit sink, sandbox profile or kill switch. Configuration that changes capabilities should require a trusted deployment path and produce auditable change events.

Detect control-loss signals: unexpected tool discovery, repeated attempts to widen scopes, disabling telemetry, self-spawning beyond limits, persistence writes to privileged locations, unexplained egress, and behavior continuing after task cancellation. Couple detection with immediate revocation and state quarantine.

A beginner-friendly reference for the security, identity, reliability, MCP, multi-agent and evaluation terms used throughout this masterclass. Closely related concepts are intentionally grouped so learners understand the differences, not just individual definitions.

Core Security Language

Guardrail
Plain English

A control that influences, constrains, detects, contains, or recovers from unsafe agent behavior. It can be a prompt rule, classifier, authorization check, hard limit, sandbox, approval, alert, or kill switch.

Why it matters

Beginners often equate guardrail with a text filter. In production, the strongest guardrails often sit outside the model and constrain what it can actually do.

OrderCare example

OrderCare may be persuaded to request a $430 refund, but the refund service still enforces the allowed amount.

Related: soft control · hard control · defense-in-depth
Threat, Vulnerability, Exploit & Compromise
Plain English

A threat is something that could cause harm. A vulnerability is a weakness that makes the harm possible. An exploit is a concrete way of using that weakness. Compromise means the attacker or failure has gained influence or capability beyond what was intended.

Why it matters

These words describe different stages of risk. Mixing them leads to vague statements such as ‘prompt injection is a vulnerability’ without naming what can actually be harmed.

OrderCare example

Threat: malicious KB content. Vulnerability: retrieved text can influence tool planning. Exploit: planted refund instruction. Compromise: the model attempts an unauthorized refund.

Related: attack · adversary · failure mode
Threat Modeling
Plain English

A structured process for identifying what is valuable, who or what can influence the system, where trust changes, what authority is available, what must never happen, and which controls enforce that.

Why it matters

It prevents teams from blindly applying generic AI-safety checklists. The threat model connects each guardrail to a real asset and failure path.

OrderCare example

For OrderCare, map customer PII, refund authority, email sending, memory, MCP tools, and code execution before choosing controls.

Related: asset · entry point · trust boundary · invariant
Asset
Plain English

Anything whose disclosure, alteration, loss, misuse, spending, execution, or persistence would matter to the business or user.

Why it matters

Security starts by asking what can actually be harmed, not by starting with the attack technique.

OrderCare example

OrderCare assets include customer PII, refund balance, send-email authority, credentials, memory, and audit evidence.

Related: data asset · capability · side effect
Actor, Adversary & Attacker-Controlled Input
Plain English

An actor is any human or system interacting with the agent. An adversary is an actor trying to cause harm. Attacker-controlled input is any field, document, tool result, peer message, or metadata an attacker can influence—even indirectly.

Why it matters

The attacker may never be the chat user. A benign user can trigger malicious content planted earlier in a webpage, ticket, email, or MCP tool result.

OrderCare example

A public forum post scraped into OrderCare’s KB is attacker-controlled even when the customer asking the later question is legitimate.

Related: direct injection · indirect injection · source provenance
Entry Point & Attack Surface
Plain English

An entry point is where influence can enter the system. The attack surface is the full set of entry points and capabilities that could be abused.

Why it matters

Agentic systems have more entry points than chat: retrieval, tools, memory, peer agents, uploaded files, MCP metadata, browser pages, and code comments all count.

OrderCare example

OrderCare’s attack surface includes chat, KB retrieval, API responses, MCP descriptions, long-term memory, sub-agent messages, and approval workflows.

Related: trust surface · capability surface
Trust Boundary
Plain English

A point where the trust level, identity, tenant, privilege, persistence, or side-effect class changes. It is not limited to a network boundary.

Why it matters

Every boundary is a place where assumptions should be revalidated. Agent systems have semantic trust boundaries as well as network ones.

OrderCare example

A KB chunk entering model context is one boundary; the model’s refund amount entering the payments API is another.

Related: authority transition · provenance · reference monitor
Authority
Plain English

The real ability to read, change, send, spend, execute, remember, or delegate something. Authority is about what the system can make happen, not what the model merely says.

Why it matters

Agent security is fundamentally about keeping authority bounded under uncertain model behavior.

OrderCare example

The sentence ‘refund $100’ has no authority by itself. A valid call to the payments tool using a privileged token does.

Related: privilege · capability · permission
Authority-Bearing Input & Authority Transition
Plain English

Authority-bearing input is data that can directly influence a privileged action. An authority transition is the moment ordinary information becomes a request or capability that can cause a real side effect.

Why it matters

These transitions are the highest-value places to put deterministic checks.

OrderCare example

The model-generated field amount=430 becomes authority-bearing when passed to issue_refund(); the tool boundary must re-check policy there.

Related: enforcement point · side effect · reference monitor
Privilege & Privileged Action
Plain English

Privilege is elevated permission to access sensitive resources or perform high-impact actions. A privileged action uses that permission.

Why it matters

A model can be harmless while answering questions but dangerous when the same model holds payment, production-write, email-send, or shell privileges.

OrderCare example

Reading public policy is low privilege; issuing a refund or writing production data is privileged.

Related: least privilege · scope · capability
Security Invariant & Business Invariant
Plain English

An invariant is a statement that must remain true even when the model is wrong or manipulated. A business invariant is the domain-specific version of that rule.

Why it matters

Invariants turn vague security goals into deterministic engineering requirements and tests.

OrderCare example

‘A user can never refund an order they do not own’ and ‘no task can send more than 20 emails’ are invariants.

Related: policy · hard control · test evidence
Policy & Enforcement Point
Plain English

Policy states what is allowed. The enforcement point is the component that actually checks the rule before access or a side effect occurs.

Why it matters

A policy written only in a system prompt is easy to bypass. A policy enforced by the resource-owning service is much stronger.

OrderCare example

OrderCare’s refund service—not the LLM—enforces tenant ownership, amount caps, and approval status.

Related: reference monitor · authorization · resource boundary
Blast Radius
Plain English

The maximum damage one failure or compromise can cause before it is contained: money spent, records read, emails sent, tools called, data leaked, or time/cost consumed.

Why it matters

No complex system reaches zero risk. Good security limits consequences when prevention fails.

OrderCare example

A task budget limiting OrderCare to one refund and five tool calls drastically reduces blast radius even if the model is hijacked.

Related: containment · task budget · recoverability
Reversibility, Recoverability & Residual Risk
Plain English

Reversibility asks whether an action can be undone. Recoverability asks how the system returns to a safe state. Residual risk is the risk that remains after controls are applied.

Why it matters

These concepts determine whether an action can auto-execute, needs approval, or needs stronger isolation and recovery mechanisms.

OrderCare example

Drafting an email is reversible; sending it externally is less so. A residual-risk memo records what could still go wrong after the course controls are implemented.

Related: risk tier · compensation · approval
Risk Tier
Plain English

A classification of an action or workflow by potential impact, reversibility, sensitivity, and required assurance.

Why it matters

The same guardrail threshold should not be used for public-document search and production payments.

OrderCare example

OrderCare might treat read-only policy lookup as low risk, email sending as medium/high, and large refunds or shell execution as critical.

Related: release gate · human approval · residual risk
Security Theater
Plain English

A control that looks reassuring but is not meaningfully tied to an asset, invariant, measurable failure mode, or enforceable boundary.

Why it matters

Agent security is especially vulnerable to controls that demo well—such as a refusal prompt—but do not hold when the model is bypassed.

OrderCare example

A prompt saying ‘never refund over $50’ without a code-level cap is security theater if the tool accepts $500.

Related: hard control · test evidence · reference monitor

Guardrail Types & Defense Placement

Soft / Probabilistic Control vs Hard / Deterministic Control
Plain English

A soft or probabilistic control reduces the likelihood of unsafe model behavior but can miss. A hard or deterministic control applies a rule in code or infrastructure and should behave predictably for the same inputs.

Why it matters

Both are valuable, but they serve different jobs. High-impact actions should not rely only on the model policing itself.

OrderCare example

A prompt-injection classifier is soft; an authorization check rejecting a wrong tenant is hard.

Related: probability control · consequence control
Probability, Consequence, Detection & Recovery Controls
Plain English

Probability controls reduce how often bad reasoning occurs. Consequence controls bound what bad reasoning can do. Detection controls reveal suspicious behavior. Recovery controls revoke, compensate, quarantine, or restore after failure.

Why it matters

This four-part model helps students see why one perfect filter is neither realistic nor sufficient.

OrderCare example

OrderCare uses provenance to reduce hijack probability, refund caps to bound consequence, traces to detect attempts, and revocation to contain incidents.

Related: preventive · detective · containment
Preventive, Detective, Containment & Recovery Controls
Plain English

Preventive controls block or reduce the event. Detective controls identify it. Containment limits spread or damage. Recovery restores a safe and useful state. A containment control specifically limits spread or damage after prevention fails.

Why it matters

A mature design assumes prevention sometimes fails and plans for the remaining stages.

OrderCare example

Authorization prevents a cross-tenant read; alerts detect repeated denials; read-only mode contains a compromised tool; compensation reverses a side effect where possible.

Related: incident response · defense-in-depth
Defense-in-Depth
Plain English

Using multiple independent controls with different failure modes so one failure does not collapse the entire defense.

Why it matters

Adding several similar classifiers is not real depth. Independence matters.

OrderCare example

A poisoned document may fool the model and evade a classifier, yet a tenant check, refund cap, approval gate, and audit trail still protect the side effect.

Related: Swiss-cheese model · layered defense
Reference Monitor
Plain English

The authoritative component that mediates access to a protected resource and applies policy on every relevant request. It should be difficult to bypass.

Why it matters

It is the mental model for deciding where hard agent guardrails belong.

OrderCare example

OrderCare’s refund service acts as the reference monitor for refund permissions and limits; calling the service directly should not bypass the policy.

Related: enforcement point · policy engine
Model-Facing, Capability-Facing, Environment-Facing & Operations-Facing Controls
Plain English

A way to classify where a control acts: on model behavior, on permissions/tools, on the execution environment, or on monitoring/response.

Why it matters

It prevents teams from solving every problem at the prompt layer.

OrderCare example

Instruction hierarchy is model-facing; scoped tokens are capability-facing; deny-all egress is environment-facing; revocation and alerts are operations-facing.

Related: control placement · defense-in-depth
Least Functionality, Least Privilege, Least Autonomy & Least Duration
Plain English

Expose only needed features; grant only needed permissions; let the agent autonomously perform only the actions appropriate for the task; and make authority last only as long as needed.

Why it matters

These are four separate ways to reduce excessive agency.

OrderCare example

A research sub-agent gets kb:read only, cannot send email, cannot approve refunds, and receives a short-lived token.

Related: scope narrowing · task-scoped capability

Identity, Authorization & Delegation

Authentication vs Authorization vs Delegation
Plain English

Authentication asks ‘who is this?’. Authorization asks ‘may this actor do this action on this resource?’. Delegation asks ‘what subset of that authority may this agent use for this task?’.

Why it matters

Agent systems often authenticate the user correctly but then execute every tool with one overpowered service credential.

OrderCare example

The customer logs in (authentication), owns order 1042 and may request a refund (authorization), while OrderCare receives only a narrow refund capability for that order (delegation).

Related: authn · authz · capability
Identity, Principal & Tenant
Plain English

Identity describes who or what is acting. A principal is the security identity to which permissions are attached. A tenant is an isolated customer or organizational boundary in a multi-tenant system.

Why it matters

Time-to-live: how long something remains valid before expiring. It can apply to credentials, memory, approvals, caches, and task leases.

Why it matters

Short TTLs reduce stale authority and persistent poisoning.

OrderCare example

OrderCare’s capability token and high-risk approval both expire after a bounded interval.

Related: expiry · revocation
ASR
Plain English

Attack Success Rate: the fraction of adversarial test cases that achieve the defined attacker goal.

Why it matters

Always define the success condition because ‘model hijacked’ and ‘forbidden side effect succeeded’ are very different outcomes.

OrderCare example

OrderCare reports both model-hijack ASR and invariant-violation ASR.

Related: security eval · red team
CI
Plain English

Continuous Integration: automated build/test workflows that run when code, configuration, prompts, or related artifacts change.

Why it matters

Security regression tests in CI help stop known vulnerabilities from silently returning.

OrderCare example

OrderCare CI fails if any standing test violates a deterministic security invariant.

Related: release gate · regression
IR
Plain English

Incident Response: the operational process for detecting, containing, investigating, recovering from, and learning from security incidents.

Why it matters

Agents can act quickly, so IR needs fast revocation and reliable traces.

OrderCare example

OrderCare’s IR drill revokes a malicious MCP server mid-task and reconstructs affected actions.

Related: incident response · containment
5xx
Plain English

HTTP status codes in the 500–599 range indicating server-side failures.

Why it matters

Agents should not automatically retry every 5xx response without limits, idempotency, and error classification.

OrderCare example

A downstream 503 triggers bounded backoff rather than an unlimited retry storm.

Related: retry budget · backoff
tmpfs
Plain English

A temporary filesystem typically stored in memory and discarded when the environment ends.

Why it matters

It provides writable workspace without persisting files to the host or long-term disk.

OrderCare example

OrderCare’s code sandbox writes temporary analysis files to /tmp on tmpfs and destroys them after the task.

Related: ephemeral state · sandbox
YAML
Plain English

A human-readable configuration format commonly used for application, deployment, policy, and tool configuration files.

Why it matters

Configuration can change agent capabilities, so agent-writable YAML can become a control-plane bypass.

OrderCare example

A coding agent is not allowed to edit the YAML file defining its own tool allowlist.

Related: configuration · immutable policy
