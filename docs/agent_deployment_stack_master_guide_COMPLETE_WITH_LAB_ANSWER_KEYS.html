The single most important idea

There is no universally “best” deployment stack. The right stack depends on what the agent needs to do: UI style, execution duration, durable state, workers, browser/code execution, traffic pattern, security, private networking, scale, cost and the skills of the team operating it.

Domain name does not create another deployment pattern

A custom domain is a routing/branding layer on top of a stack. It can make a deployment more professional—especially for Vercel, PaaS, Cloud Run and VM—but it does not become a tenth compute architecture.

STACK A

Streamlit / Gradio Hosted

Fastest demo & internal-tool path

Usage: Hobby / Demo / tiny internal Enterprise popularity: Low Solo popularity: Very High Cost: $0–Low Complexity: Very Low

Explain it to a non-technical learner

You build both the agent and a simple web screen in Python. A managed hosting service runs that Python app and gives you a URL. You do not manage a server yourself.

When should I use this?

Typical use cases: Demos, classroom projects, hackathons, proof-of-concepts, analyst tools, tiny internal assistants, early RAG/chat prototypes.

Design call: Prefer this when speed-to-demo matters more than infrastructure control. It is ideal when the whole experience can live in one Python process and you do not need sophisticated enterprise authentication, private networking, durable background jobs, or complex multi-tenant isolation.

Key teaching point: deployment is the operational shell around the agent. It does not automatically provide the model, tools, memory, database or business logic.

Mandatory conditions

If these are not true, this stack is usually a poor fit or requires redesign.

  • Agent can run as one web process.
  • UI can be Streamlit/Gradio-style rather than a fully custom frontend.
  • Secrets can be supplied through the hosting platform.
  • Anything that must survive a restart is stored outside the temporary app process/filesystem.

Good-to-have prerequisites

Not mandatory, but they make implementation safer and easier.

  • Git repository and reproducible dependency file.
  • Hosted LLM API instead of local GPU inference.
  • Small user count and modest concurrency.
  • Managed DB/vector store if conversations or documents must persist.

How this stack works — end-to-end

  1. User opens the hosted URL.
  2. The hosting platform routes the request to your Streamlit/Gradio process.
  3. The Python UI calls your agent logic in the same application.
  4. The agent calls the LLM, tools, APIs and optional databases.
  5. The answer is rendered back in the same Python web app.

Cost implications

Usually the cheapest path. Hosting may be free for small/community use, but model/API usage can still cost money. Adding managed databases, vector stores, private networking or larger compute changes the economics.

Latency implications

The hosting layer usually adds little latency. LLM and tool calls dominate. The main risk is a sleeping/free app that needs to wake up, which can add seconds to the first interaction.

Latency means how long the user waits between an action and the response.

Cons / trade-offs

  • Weak control over advanced authentication, private networking and worker topology.
  • Local disk/process memory should not be treated as permanent.
  • Long-running browser/code-execution workloads can be fragile.
  • Scaling and tenant isolation are usually not strong enough for serious enterprise platforms.

Step-by-step implementation

1
Make the app run from a clean environment using requirements.txt or pyproject.toml.
2
Move API keys and passwords out of code; create .env.example with variable names only.
3
Identify anything written to local disk and decide whether it is safe to lose.
4
Add friendly error messages and timeouts around model/tool calls.
5
Push code to GitHub or another supported Git provider.
6
Create the hosted app and select repository, branch and Python entry file.
7
Add secrets in the hosting platform settings.
8
Deploy and test with a second browser/user.
9
Test idle wake-up, file uploads and multiple simultaneous users.
10
Add basic logs and model-cost/latency tracking.

Things to be careful about

  • Never commit secrets.
  • Do not assume uploaded/local files will survive restarts.
  • Put limits around file size and expensive tool calls.
  • Do not confuse 'works for 5 users' with 'enterprise ready'.

STACK B

Managed PaaS

Git-based small-team production

Usage: Startup / Small-team production Enterprise popularity: Medium Solo popularity: High Cost: Low–Medium Complexity: Low

Container engineering for Stack B

PaaS can build from source, but understanding Dockerfiles, health checks, secrets and CI/CD makes the deployment portable and production-ready.

Explain it to a non-technical learner

A Platform-as-a-Service (PaaS) runs your web application for you. You connect a Git repository, tell it how to start the app, and the platform handles building, restarting, routing and basic scaling.

When should I use this?

Typical use cases: Small-team production, startup APIs, internal business tools, moderate-traffic agent apps, API + worker architectures.

Design call: Prefer PaaS when you want real production behavior but do not want to become an infrastructure team. It is the practical middle ground between demo hosting and full cloud-native architecture.

  4. Short agent work runs inside the request.
  5. Long work can be placed on a queue and processed by a worker.
  6. Managed DB/Redis/object storage keep state independent of the web instance.

Cost implications

Usually inexpensive for one or two small services. Cost grows with always-on web + worker instances, managed Postgres/Redis, bandwidth and observability. LLM/tool usage may still dominate the bill.

STACK C

Cloud Run + Managed State

Serverless containers for bursty APIs

Usage: Production / Serverless Enterprise popularity: High Solo popularity: Medium–High Cost: $0-ish–Medium Complexity: Low–Medium

Hands-on companion for Stack C

Explain it to a non-technical learner

You package the agent as a container. Google Cloud runs that container only when needed, automatically creates more copies when traffic grows, and can scale it down when traffic disappears.

When should I use this?

Design call: Prefer this when the agent is naturally an HTTP/API service and its durable state can live outside the container. It is especially attractive when traffic is irregular and you want to pay mainly for usage.

Cost implications

The infrastructure baseline is often meaningful: cluster/node compute, ingress/load balancers, observability and platform services. It can be efficient at large scale because many workloads share the platform, but inefficient for one small app.

Latency implications

Warm pods provide predictable latency. However, ingress, service mesh sidecars and cross-service calls add overhead. Scaling a new node—especially a GPU node—is slower than starting another warm pod.

Latency means how long the user waits between an action and the response.

  • Easy to over-engineer a small agent.
  • Cluster networking, upgrades, security and debugging require specialized skills.

Docker Fundamentals: image → container → repeatable runtime

Must Know
Start with the problem

Your FastAPI + LangChain agent works on your laptop but fails on another engineer’s machine because Python and system-library versions differ.

Concept reveal: Package the application and its dependencies into a Docker image, then run that image as a container.

Why it matters: Containers solve environment consistency. They do not automatically solve state, scaling, security or orchestration.

The four ideas to understand first

  • Image: a packaged, read-only blueprint containing OS-level pieces, Python runtime, dependencies and application files.
  • Container: a running instance of an image. One image can start many containers.
  • Layer: each Dockerfile instruction typically contributes a reusable filesystem layer.
  • Build cache: Docker can reuse unchanged layers, dramatically speeding rebuilds.

Why layers and cache matter

Consider two Dockerfiles. Both work, but one rebuilds dependencies every time any source file changes.

Cache-unfriendly

COPY . /app
RUN pip install -r /app/requirements.txt

Cache-friendly

COPY requirements.txt /app/
RUN pip install -r /app/requirements.txt
COPY . /app

Because dependency installation changes less frequently than application code, separating the steps lets Docker reuse the expensive dependency layer.

docker build -t agent-api:dev .

# See local images
docker images

# Run and map host port 8080 to container port 8080
docker run --rm -p 8080:8080 --name agent-api agent-api:dev

docker ps

# Follow application logs
docker logs -f agent-api

# Open a shell inside a running container
docker exec -it agent-api sh

# Stop
docker stop agent-api

Container lifecycle mental model

created → running → stopping → exited → removed

A container should be treated as replaceable. Durable user data should normally live in a database, object store, or deliberately managed volume—not accidentally inside the container filesystem.

Mini knowledge check

You rebuild after changing only app.py, but pip installs everything again. What concept should you investigate?
Docker layer ordering and build cache. Copy stable dependency manifests before frequently changing source files.
If one image starts three containers, do you now have three images?
No. You have one image and three running container instances.
PACKAGE FOR PRODUCTION

Writing a production Dockerfile for FastAPI + LangChain

Must Know
Start with the problem

A demo Dockerfile runs as root, copies every local file, installs compilers in the final image, and takes 1.2 GB. A vulnerability scan shows a huge attack surface.

Concept reveal: Production Dockerfiles optimize reproducibility, cache efficiency, small runtime footprint, non-root execution and clean process behavior.

Why it matters: The Dockerfile becomes part of your security and deployment architecture.

Start with the deliberately bad version

FROM python:3.12
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
  • Copies secrets, caches and local clutter unless excluded.
  • Dependency layer is invalidated whenever any source file changes.
  • Runs as root unless changed.
  • Uses a broad base image rather than a smaller production base.
  • No explicit production server command or predictable port.
  • Build-only packages can remain in the production image.

A stronger single-stage FastAPI pattern

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Install dependencies first for better build-cache reuse
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code after dependencies
COPY app/ ./app/

# Run as an unprivileged user
RUN useradd --create-home appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 8080

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
Important: `EXPOSE 8080` documents the intended container port. It does not itself publish the port to the internet.

Multi-stage builds

Problem: some Python packages require compilers or OS headers to build. You need them while creating dependencies—but not necessarily while running the final app.

Builder stagecompiler · headers · wheels
→ copy only built artifacts →
Runtime stagePython + runtime libraries + app
# ---------- builder ----------
FROM python:3.12-slim AS builder
WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends build-essential \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

# ---------- runtime ----------
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /wheels /wheels
COPY requirements.txt .
RUN pip install --no-cache-dir --no-index --find-links=/wheels -r requirements.txt \
    && rm -rf /wheels
COPY app/ ./app/
RUN useradd --create-home appuser && chown -R appuser:appuser /app
USER appuser
EXPOSE 8080
CMD ["uvicorn","app.main:app","--host","0.0.0.0","--port","8080"]

Production checklist

  • Use a maintained, appropriately small base image.
  • Pin application dependencies using a reproducible lock/requirements strategy.
  • Copy dependency manifests before source for cache efficiency.
  • Use `.dockerignore`.
  • Run as a non-root user where feasible.
  • Do not bake API keys or `.env` files into the image.
  • Keep one clear foreground process as PID 1.
  • Make SIGTERM/graceful shutdown work.
  • Add image scanning in CI.
  • Tag releases immutably (Git SHA or semantic version), not only `latest`.

Must Know
Start with the problem

An engineer adds `ENV OPENAI_API_KEY=sk-...` to a Dockerfile and pushes the image to a registry.

Concept reveal: Secrets must be injected at runtime—not baked into source code or image layers.

Why it matters: Image history and registries can preserve sensitive values even if you later edit the Dockerfile.

Configuration vs secret

Configuration

Non-sensitive runtime choices such as `LOG_LEVEL=INFO`, `MODEL_NAME=gpt-x`, `REGION=asia-northeast1`.

Secret

Passwords, private keys, API keys, DB credentials and tokens whose disclosure creates risk.

SAFE TRAFFIC & TERMINATION

Liveness, readiness and graceful shutdown

Must Know
Start with the problem

A new container process has started, but its database connection pool and model configuration are not ready. The load balancer immediately sends customer traffic and requests fail.

Concept reveal: Separate liveness ('is the process alive?') from readiness ('can it safely receive traffic?').

Why it matters: Health checks determine whether platforms start, stop and route traffic to container instances.

Three distinct concepts

Liveness

Is the process alive, or has it deadlocked/crashed?

Should usually be cheap and avoid fragile downstream dependencies.
Readiness

Can this instance safely receive new traffic?

May validate critical startup state/dependencies.
Graceful shutdown

When termination starts, can in-flight work finish cleanly?

Stop accepting work, close connections, flush telemetry, exit.

FastAPI example

from fastapi import FastAPI
import asyncio

app = FastAPI()
ready = False

@app.on_event("startup")
async def startup():
    global ready
    # Initialize clients, validate config, warm required resources
    ready = True

@app.get("/health/live")
def live():
    return {"status": "alive"}

@app.get("/health/ready")
def readiness():
    if not ready:
        from fastapi import HTTPException
        raise HTTPException(status_code=503, detail="not ready")
    return {"status": "ready"}

@app.on_event("shutdown")
async def shutdown():
    global ready
    ready = False
    # Close DB/Redis/HTTP clients and stop taking new jobs
    await asyncio.sleep(0)

Compose health check example

services:
  api:
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request; urllib.request.urlopen('http://localhost:8080/health/live')"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s

Agent-specific shutdown risks

  • Do not pull a new queue job after shutdown begins.
  • Decide whether long agent runs can finish, checkpoint or be safely retried.
  • Make external side effects idempotent.
  • Close DB/Redis clients cleanly.
  • Flush traces/log buffers before exit.
  • Use platform timeout/grace-period settings compatible with the application.

Illustrative GitHub Actions workflow for Cloud Run

name: deploy-agent

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write

env:
  REGION: asia-northeast1
  SERVICE: agent-api

      - uses: actions/setup-python@v5

      # Prefer workload identity / OIDC rather than a long-lived JSON key.
      - name: Authenticate to Google Cloud
        uses: google-github-actions/auth@v3
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_DEPLOY_SERVICE_ACCOUNT }}

      - uses: google-github-actions/setup-gcloud@v3

      - name: Configure Docker auth
        run: gcloud auth configure-docker $REGION-docker.pkg.dev --quiet

      - name: Build and push
        run: |
          IMAGE="$REGION-docker.pkg.dev/${{ secrets.GCP_PROJECT_ID }}/$REPOSITORY/$SERVICE:${{ github.sha }}"
          docker build -t "$IMAGE" .
          docker push "$IMAGE"

      - name: Deploy
        run: |
          gcloud run deploy "$SERVICE" \
            --image "$IMAGE" \
            --region "$REGION" \
            --quiet

      - name: Smoke test
        run: |
          URL=$(gcloud run services describe "$SERVICE" --region "$REGION" --format='value(status.url)')
          curl --fail "$URL/health/live"

  • Optional: agent regression/evaluation gate fails.

SAFE RELEASE STRATEGIES

Blue/Green and Canary: change the agent without betting 100% of users

Production Maturity
Start with the problem

Version 2 passes unit tests but subtly chooses the wrong tool more often. A 100% instantaneous rollout would expose every user before the problem is visible.

Concept reveal: Separate 'deployment succeeded' from 'new version is actually good'. Use controlled traffic migration.

Why it matters: Agent releases need infrastructure metrics AND task-quality/evaluation metrics.

Blue/Green deployment

Router / Load Balancer
BLUEcurrent production v1
GREENcandidate v2

Pattern: deploy Green separately → test it → switch production traffic from Blue to Green → keep Blue available for rapid rollback.

  • Pros: clear environment separation, fast switch/rollback, easy smoke testing.
  • Cons: duplicate capacity can cost more; DB/schema compatibility must be considered.

Canary deployment

v1
95%
v2
5%

Start with a small percentage of traffic on v2, evaluate it, then move 5% → 10% → 25% → 50% → 100% if healthy.

For agents, monitor two scoreboards

Infrastructure health

  • HTTP error rate
  • p95 latency
  • CPU/memory
  • instance/task count
  • queue backlog
  • dependency failures

Agent quality

  • task success / eval score
  • tool-call error rate
  • wrong-tool / wrong-action rate
  • RAG retrieval quality
  • human escalation rate
  • token/cost per successful task
Key lesson: a release can have 0 HTTP errors and still be a terrible agent release.

Cloud Run practical mapping

Cloud Run creates immutable revisions. You can deploy a new revision without immediately routing traffic to it, then split percentages across revisions and roll back by moving traffic to an older revision.

RUN IT SAFELY

Monitoring deployed containers + container security

Production Maturity
Start with the problem

The container is 'up', but users report slow answers and incorrect tool actions. CPU is normal, so infrastructure monitoring says everything is green.

Concept reveal: Production agents require infrastructure + application + agent-level observability.

Why it matters: Containers solve packaging; observability and security make them operable.

Three monitoring layers

InfrastructureCPU · memory · instance count · restarts
Applicationrequests · HTTP errors · p50/p95 latency · queue depth
AgentLLM/tool latency · token cost · trace · evals · task success

Cloud Run monitoring demo checklist

  1. Deploy and generate test traffic.
  2. Open Cloud Run service metrics and note request count, latency and container instances.
  3. Open logs; filter by service/revision.
  4. Emit structured application logs with request/correlation ID.
  5. Force a controlled error and verify it is visible.
  6. Configure an alerting policy for a meaningful signal such as elevated error rate or latency.
  7. Correlate infrastructure request ID with agent trace ID in Langfuse/LangSmith/OpenTelemetry if used.
  8. During a canary, compare v1 versus v2 both operationally and on agent eval/business metrics.

Container security checklist

  • Minimal base image: fewer unnecessary packages means smaller attack surface.
  • Non-root runtime: avoid root inside the container unless genuinely required.
  • No secrets in images: inject at runtime.
  • Pin and update dependencies: control supply-chain drift.
  • Image vulnerability scanning: run in CI/registry and establish severity policy.
  • Least privilege: task/service account only gets permissions it needs.
  • Network restrictions: expose only required ports and private dependencies.
  • Resource limits: prevent one workload from consuming the entire host/service budget.
  • Read-only filesystem where practical: reduce accidental/hostile writes.
  • Advanced: SBOM, image signing/provenance and policy enforcement.

Glossary of deployment terms

Plain-English explanations of the technical words used throughout the guide.

Agent

Software that uses a model to reason, choose actions/tools and continue until it reaches a goal.

API

Application Programming Interface. A structured way for one program to call another, commonly over HTTPS.

Backend

The server-side part of an application: agent logic, APIs, databases, tool calls and business rules.

Frontend

The user-facing web/mobile interface.

Container

A packaged application plus its dependencies. Docker is the most common container tool.

Dockerfile

A recipe that explains how to build a container image.

Container image

The packaged, read-only artifact built from a Dockerfile.

Docker Compose

A simple way to define and run several containers together on one machine.

VM / Virtual Machine

A software-defined computer running its own operating system on cloud hardware.

PaaS

Platform as a Service. A provider runs much of the infrastructure; you mainly supply application code.

Serverless

A billing/operation model where the provider manages servers and automatically allocates compute when needed.

Function / FaaS

A small piece of server-side code triggered by an event; FaaS means Function as a Service.

Cold start

Delay when a platform must create or initialize a new runtime before handling a request.

Scale to zero

The platform can reduce running instances to zero when idle, cutting compute cost.

Autoscaling

Automatically increasing/decreasing the number of running application instances.

Concurrency

How many requests/jobs one process or instance handles at the same time.

State

Information that must be remembered: user session, workflow position, database records, uploaded files, etc.

Ephemeral

Temporary. Ephemeral local files/process memory can disappear when an instance restarts.

Durable state

Information stored in a system designed to survive restarts, such as Postgres or object storage.

Postgres

A widely used relational database often used for durable application/session data.

Redis

A fast in-memory data store frequently used for caching, queues and short-lived coordination.

Vector database

A database optimized for similarity search over embeddings; commonly used in RAG.

Object storage / Blob storage

Low-cost durable storage for files such as PDFs, images, reports and model artifacts.

RAG

Retrieval-Augmented Generation: retrieve relevant information first, then give it to the model for answering.

Queue

A buffer that stores jobs/messages until a worker can process them.

Worker

A background process that consumes jobs from a queue.

Webhook

An HTTP call sent automatically when an external event occurs.

Cron / Schedule

A rule that triggers work at a specific recurring time.

Workflow orchestrator

A system that coordinates multi-step tasks, retries, waits, branching and state.

Idempotency

Property that safely performing the same operation more than once has no unintended extra effect.

Retry

Automatically trying a failed operation again.

Dead-letter queue (DLQ)

A place where repeatedly failed queue messages are kept for investigation or replay.

SSE

Server-Sent Events. A simple HTTP mechanism for streaming events/tokens from server to browser.

WebSocket

A persistent two-way connection between client and server, useful for real-time interaction.

Reverse proxy

A front-door server that receives internet traffic and forwards it to internal app services.

TLS / HTTPS

Encryption that protects traffic between users and the server.

DNS

The system that maps a domain name such as app.example.com to a server/service.

Custom domain

A domain you own and map to your hosted application.

Load balancer

Distributes requests across multiple healthy application instances.

Health check

A lightweight endpoint used to confirm an application is alive and ready.

IAM

Identity and Access Management: rules controlling which user/service may access which resource.

Workload identity

A cloud identity assigned to a running service, avoiding long-lived API keys.

RBAC

Role-Based Access Control: permissions grouped into roles.

SSO

Single Sign-On: users authenticate through a centralized enterprise identity provider.

VPC / VNet

A private cloud network where services can communicate under network rules.

Private endpoint

A way to access a cloud service without routing traffic through the public internet.

NAT

Network Address Translation. Often used for private workloads to reach the public internet; can create cost.

Ingress

The component/rules that bring external traffic into a Kubernetes cluster.

Pod

Kubernetes' smallest deployable unit, usually containing one application container.

Node

A machine in a Kubernetes cluster that runs Pods.

Service mesh

An infrastructure layer for service-to-service networking, security and telemetry.

CI/CD

Continuous Integration / Continuous Delivery: automated test, build and deployment pipeline.

Infrastructure as Code (IaC)

Defining cloud resources in code using tools such as Terraform rather than manual console clicks.

Observability

Logs, metrics and traces that help you understand system behavior.

Trace

A record that follows one request/workflow across multiple services and tool/model calls.

SLO

Service Level Objective: a reliability target, such as 99.9% successful requests.

HA / High Availability

Design that keeps service running despite component failures.

RTO

Recovery Time Objective: maximum acceptable time to restore service after a failure.

RPO

Recovery Point Objective: maximum acceptable amount of data loss measured in time.

Multi-tenant

One system serves separate customers/organizations while keeping their data and permissions isolated.

Data residency

Requirement that data remains in a specified country/region.

MCP

Model Context Protocol: a standard way for AI systems to discover and call tools/data services.

Agent runtime

The execution environment that runs an agent, manages sessions and often integrates tools/memory.

Agent identity

The machine/service identity under which an agent accesses enterprise tools or data.

Latency

Time between a user action and the resulting response.

Throughput

Amount of work handled per unit time.

GPU

Graphics Processing Unit; commonly used for local model inference and compute-intensive AI workloads.

How to read this guide

Volatility watch

What this guide deliberately separates

  • Deployment architecture — where/how code runs.
  • Domain/DNS — how users reach it.
  • Model provider — which LLM you call.
  • State services — DB/vector/object storage.
  • Agent framework — LangGraph, OpenAI Agents SDK, Agent Framework, CrewAI, etc.
