# Stage 5: Memory & State Design

**Revision note:** this replaces the prior draft. Stage 4 was revised to add a `search_similar_incidents` tool per the user's request: the system must retain a full history of past incidents and their outcomes, and check for a similar precedent before spending search effort re-identifying the repo/file for a new incident. This reverses the earlier "long-term knowledge: not needed" call — a similarity-searchable store of past incidents is exactly what that category means. Stage 2's pattern is unchanged (still bounded ReAct, not RAG) — this is one additional retrieval tool call at the start of the existing loop, not a pattern change.

## Per-category decisions

| Category | Needed? | Store type | Scope / TTL | Rationale |
|---|---|---|---|---|
| Conversation context | Yes, minimal | In-context only (LangGraph's message/state list for the current graph run) | Per-task-instance; discarded once the incident's run completes | Unchanged from prior draft — one incident description drives one bounded ReAct loop; no multi-turn dialogue to retain beyond the run itself. |
| User preferences | **Not needed** | — | — | Unchanged — single anonymous dev/SRE persona, no return-user personalization implied. |
| Task/scratch state | **Yes** | LangGraph checkpointer, SQLite (per stage 3) — incident text, identified repo, root cause, drafted patch, draft ticket, approval status (`pending`/`approved`/`rejected`), and now also which precedent (if any) `search_similar_incidents` matched | Per-task-instance; persists from submission until the incident reaches a terminal state | Unchanged rationale from prior draft — stage 3's durability requirement is unaffected by the new tool; the precedent match found is simply one more field carried in the same checkpointed state. |
| Business records | **Yes** | Reuse existing local stores: the 3 synthetic repos as files on disk, and the mocked Jira ticket store as local JSON | Long-lived, survives restarts | Unchanged from prior draft. |
| Long-term knowledge | **Yes — reversed from prior draft** | The same SQLite `incidents` table doubles as the long-term-knowledge store: each row includes the incident text, an embedding of that text, identified repo, root cause, patch outcome. `search_similar_incidents` computes similarity **in-process** (cosine similarity over stored embedding vectors, done in Python at query time — no separate vector database) and returns the best match above a similarity threshold, or none. | Long retention, same lifetime as audit history — a precedent from an old incident stays useful indefinitely for this demo | This is genuinely long-term knowledge (past incidents + outcomes, referenced when diagnosing new ones), but it does **not** warrant a dedicated vector store (Chroma/FAISS/Qdrant) — the brief's own scale (single-digit incidents per demo session, 3 small repos) means a full vector DB would be infrastructure the demo doesn't need. A single OpenAI embedding call per new incident description, compared in-process against a handful of stored embeddings, is simpler, cheaper, and just as correct at this scale. Stage 2's pattern is preserved: this is `search_similar_incidents` as one more bounded tool call in the existing ReAct loop, not a switch to a RAG architecture. |
| Audit history | **Yes** | Same append-only **incident history table** as before (SQLite, `incidents`), now also serving as the long-term-knowledge source above — one table, two uses | Long retention, no TTL/expiry in this demo | Unchanged core rationale, but now explicitly double-duty: the row that records what happened (audit) is the same row `search_similar_incidents` reads when looking for a precedent (knowledge). Columns: `incident_id, incident_text, incident_embedding, identified_repo, root_cause_summary, classification (code/infra), matched_precedent_id (nullable), ticket_id, patch_diff, approval_status, test_result, closed_at, created_at`. |

## Cross-checks against stages 3-4

- **Task/scratch state ↔ stage 3**: unchanged — SQLite-backed LangGraph checkpointer spans the human-approval interrupt, now also carrying the matched-precedent field.
- **Audit history ↔ stage 4**: covers all six audited tools from the revised stage 4 (`search_similar_incidents`, `run_tests`, `draft_patch`, `create_jira_ticket`, `apply_patch`, `close_jira_ticket`) — each writes or updates a field on the same `incidents` row.
- **Long-term knowledge ↔ stage 4's new tool**: `search_similar_incidents` reads directly from the `incidents` table's embedding column — no new storage layer was introduced beyond what audit history already required; the two categories share one physical table by design, not by accident.
- **Scope note on the precedent shortcut**: per the user's explicit instruction, a matched precedent only shortcuts *finding* the repo/file (skips `list_repos`/`search_code` iteration) — the agent still runs `read_file` on the precedent-indicated file(s) and independently reasons about the current incident's root cause and patch via `draft_patch`; it never reuses a past patch verbatim. This constraint should be carried forward into stage 7 (loop engineering), since it changes the loop's early steps conditionally based on whether a precedent was found.
